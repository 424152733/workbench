# 多保单保障缺口分析实施计划

**状态：** 首版已实施（2026-11-01）；家庭级汇总和逐项人工核对仍待后续迭代<br>
**目标：** 让保险业务员能从客户的多份保单中看清“谁被保障、保障什么、金额怎么算、每年交多少”，检查医疗保障链条、家庭身故兜底和年金现金流安排，并把分析转成客户服务和后续展业机会。

### 首版已经交付

- 客户详情新增“保障检视”，从客户名下多张保单与已整理合同汇总医疗、重疾、意外、寿险和年金记录。
- 产品按保单险种/产品名称归类；重疾、意外等产品附带的身故给付单独列为一项身故责任，不把整份保单误称为寿险，也不据此直接认定已配置独立寿险兜底。
- 保障明细按责任名称去重；同名且金额不冲突时合并不同页资料、保留来源页，责任金额冲突时仍分别展示并待核。仅明确命名为理赔申请、申请材料或报案流程的行政信息不当作保险金展示；不能因保障条件提到医院、诊断资料或理赔流程而过滤真实责任。没有单独金额或给付方式的疾病定义（包括衰竭、失代偿、移植类名称）在“疾病定义范围”中逐项展示名称、合同页码和可识别的定义条件，与保险金给付项目分区呈现。合同完整且有结构化责任时，隐藏重复的自由文本责任摘要。
- 重疾责任分类覆盖轻症、中症、重大疾病等表述；只展示合同明确识别到的责任，不根据产品名称补造保障。
- 医疗险明确包含的住院及住院前后门急诊责任，若共用一般医疗年限额，在摘要中说明共用关系；理赔服务指引不作为独立保险金项目展示。
- 合同整理结果的待核提示与已识别的公司、产品和医疗年限额交叉校验，避免同一结果一边显示具体数据、一边仍提示未识别。
- 展示层分工明确：合同整理区用于单份合同识别和核对，已归档合同默认收起重复的整份识别结果；保障检视只保留总览指标和按类型的完整责任明细，不再重复铺一套按保单的摘要卡片。
- 以已核实、当前有效、被保险人为当前客户的记录作为个人初筛依据；其他家庭成员、待核实和非在保记录分开呈现，不混进个人有效保障统计。
- 提供医保、单位补充医疗、家庭收入责任、经济依赖人数、房贷和长期目标等简短补充项；未填信息会显示为待确认。
- 规则在本地汇总并生成可转跟进事项的服务提醒，不调用模型，不增加合同整理的 token 消耗。
- 保障类型明细会在本机读取已上传原 PDF 的保单页和可核对责任条款；原合同与已登记保单按产品名及生效日精确匹配，避免重复列出。能识别但尚未归档的合同单独作为“合同待归档 · 状态待核”列入对应类型；其责任和保额只计入“含待核”口径，不当作已核实有效保障。上传、删除、整理或归档合同后，保障检视自动刷新。
- “初筛出的服务重点”由已登记保单和客户保障资料即时推导，不单独保存。客户名下已登记保单为零时，服务重点清空并显示空状态；新增或重新归档保单后再生成。客户保障档案、家庭情况和跟进记录不随之删除。
- 身故保险金可作为重大疾病保险的附带身故责任列在“身故责任”下，但该保单仍按重疾产品归类；条款中的“因意外”是给付原因，不据此推定有独立意外险。原 PDF 中的页码统一标明为 PDF 页码。医疗合同到期后是否续保、实际缴费和保单效力需人工确认。
- 多倍保障合同的“前10年关爱保险金”既可随符合条件的重疾，也可随符合条件的身故给付，故在相应两栏展示同一项附加责任；“特定严重疾病保险金”单独列在重疾给付下，避免把两项不同条件与比例合成一条。
- 支持下载自包含 HTML 摘要，可打印或另存为 PDF；摘要包含概况、分类保单、服务建议和核对边界，不展示合同原文摘录。

首版定位是**客户服务初筛**，不是自动承保评估或具体产品推荐。暂未实现家庭成员层级的需求档案、保障责任逐条人工确认与修正、复杂保费频率换算和家庭汇总。详细范围见文末“当前实现与后续迭代”。

## 1. 产品目标与分析边界

核心结果是帮助业务员完成一次有依据的保单检视：

> 现有保单和家庭情况 → 医疗保障链条 + 家庭身故兜底 + 年金现金流安排 → 说明缺口和理由 → 形成客户沟通、补资料和后续跟进动作。

第一版以**单个客户档案**为入口，支持同一客户名下多份保单；客户已有家庭档案时，按家庭成员分别汇总，不把投保人误当成被保险人。建议分为三类：

- **资料待补：** 缺少被保险人、责任金额、缴费方式、保单状态等关键信息。
- **可能存在缺口：** 已有资料提示某类风险保障不足，说明依据和不确定性。
- **展业机会：** 识别客户当前最值得继续沟通的保障问题，给出建议询问的问题、需补充的资料和可讨论的保障方向；不在需求未确认前直接推具体产品。

“档案暂无记录”只能表述为“当前档案未查到”，不能推断客户现实中没有保险。未核实、已失效、未生效或保障对象不明的保单，不计入已确认的当前保障，但要单独展示。

## 2. 当前基线与主要缺口

当前合同整理已支持逐份 PDF 上传、逐份提取责任与保费、人工核对后保存为待核实保单；家庭保障初筛能按家庭成员和医疗、重疾、寿险、意外等分类统计记录状态。但目前还没有：

1. 把合同中不同保障责任存成可计算、可人工修正的结构化项目；现有保额和保费字段多为自由文本。
2. 按被保险人汇总多份有效保单的同类保障金额与年交保费。
3. 区分医疗报销额度、重疾一次性给付、身故保额、意外伤残给付、津贴和年金等不同口径。
4. 收集判断保障是否匹配所需的少量家庭情况；没有这些信息时，不能可靠判断“够不够”。
5. 把缺口依据、信心程度、待确认问题和下一步建议展示在同一处。

已有家庭成员与保单角色关联、合同状态、保单分类标签可复用，避免另建一套家庭和保单台账。

## 3. 建议的用户流程

### 3.1 整理多份合同

客户详情中继续逐份上传合同，合同分别解析、分别授权、分别人工核对。整理后可将每份合同保存为待核实保单，并确认被保险人、保障分类、缴费信息和在保状态。合同之间不合并发送给模型。

### 3.2 建立保障概览

在客户保单区域增加“保障概览 / 缺口初筛”，提供：

- 当前已核实且有效的保单数、待核对数和无法确认状态数。
- 按被保险人分组的保障卡片：医疗、重疾、寿险、意外；养老年金和财产险另列，不混入人身风险金额合计。
- 各保障类型下列出纳入的保单和合同责任，显示金额口径、期限、有效状态及来源合同/页码。
- 汇总已确认的年度缴费支出；单次缴费、月缴和缴费频率不明的记录分开标识，不强行换算。
- “资料缺失 / 需要确认 / 可能缺口 / 暂未发现明显资料缺口”状态，以及触发该状态的具体理由。

### 3.3 补充客户情况并形成服务与展业建议

通过简短表单补齐分析所需信息，并允许选择“暂不提供”：基本医保类型/参保状态、单位补充医疗、家庭主要收入来源、经济责任人、被抚养人数、房贷等主要负债、已有商业医疗保障、家庭预算范围和职业风险等。优先采用区间或选项，不要求收集与判断无关的敏感细节。

系统根据已核实保障和客户情况生成解释性初筛。每条结论都显示“为什么这样提示”“还缺什么信息”“下一步怎么服务客户”，并可转成保单复核、补资料、家庭保障沟通等跟进事项。业务员确认客户需求和预算后，再进入具体产品方案讨论。

## 4. 数据结构和口径

### 4.1 保障责任结构化

在现有 `policies` 与合同整理记录之上增加可核对的保障责任明细。每条明细至少包括：

- 所属保单、保障对象/被保险人、保障分类和责任名称。
- 金额与单位、金额口径、给付方式、保障期间、缴费相关信息。
- 责任条件/限制的简要说明、合同页码、来源及人工核实状态。
- 未识别或无法统一的字段保持为空，并说明待核对原因。

分类和金额口径需覆盖报销限额、一次性给付、按比例给付、每日/每月津贴、年金、身故责任、伤残责任等。不得把这些不同含义的数字加成一个“总保额”。

### 4.2 保费

保费需要保存金额、币种、缴费频率、缴费期限和是否趸交。概览中展示“当前已确认年交保费”；只有合同明确频率时才换算（月缴 × 12 等）。趸交金额独立显示；频率不清、首期与续期不同或金额无法辨认时标为待核实。不要把年交保费乘以缴费年限后当成当前年度成本。

### 4.3 在保状态和纳入规则

- 仅“已人工核实 + 当前有效 + 已确认被保险人”的责任进入已确认保障汇总。
- 待核实、状态未知、待生效、已终止、已过期分别展示，不与有效责任混算。
- 一份合同可有多项责任；一个被保险人可对应多份合同；同一家庭保单按保单 ID 去重。
- 投保人和被保险人分开保存、分开展示。
- 对责任冲突、重复责任或无法判断能否叠加的情况，不擅自去重或相加，改为并列展示并提示人工核实。

## 5. 缺口判断与展业建议规则

### 5.1 第一版先做透明规则，不让模型决定是否“足够”

模型继续负责从单份合同中提取结构化事实；多保单归并、数值汇总、状态过滤和缺口初筛全部在本地使用确定性规则完成，不把全部合同再次发给模型。AI 可以辅助把已确认的分析结果改写成易懂说明，但不能补造金额、目标、适用性或结论。

判断结果使用明确等级：

1. **资料不足，无法初筛**：被保险人或关键责任字段缺失，或没有可计入的已核实有效保单。
2. **建议进一步核对**：有同类保障记录，但金额口径、期限、责任限制、医保/单位福利或家庭需求不清楚。
3. **提示可能存在缺口**：已填客户情况与已确认保障对照后，出现明确的待覆盖风险；说明这只是初筛，不是购买结论。
4. **当前资料暂未发现明显缺项**：只表示按已录入需求和资料未发现规则触发项，不代表全面充足。

### 5.2 主线一：医疗保障链条是否完整

医疗保障不只看“有没有一张医疗险”，而是检查每一层是否存在、是否有效、责任是否清楚：

1. **基础医保：** 职工医保、居民医保、其他或未参保/未知；同时确认是否有单位补充医疗。
2. **住院及大额医疗费用：** 是否有商业医疗费用补偿责任；重点核对年度/终身限额、免赔额、报销比例、医院和费用范围、续保条件及既往症限制。
3. **疾病后的收入和康复支出：** 是否有重疾等一次性给付保障；单独呈现给付条件和金额，不把它当作医疗报销额度。
4. **意外医疗与伤残：** 单独检查意外医疗、意外伤残和意外身故责任，不能因为有普通医疗险就推定意外责任齐全。

初筛可将“基础医保未确认”“没有已核实的住院费用保障”“只查到给付型保障、没有费用报销责任”“医疗责任续保/限额等关键条件不明”列为待服务问题。系统不依据保单名称猜责任，也不自动断言客户没有保障；先确认系统外保单、单位福利和合同责任。

### 5.3 主线二：家庭责任人是否配置兜底资金，并看清寿险的双重属性

寿险产品范围包括定期寿险、终身寿险、增额终身寿及分红型终身寿等，不把寿险等同于定期寿险或单纯的“高杠杆工具”。先确认谁承担主要家庭收入、是否有配偶/子女/父母等经济依赖者、房贷等长期负债及现有身故保障。产品按保单险种/产品名称归类；重疾、意外等产品附带的身故给付可作为身故责任单独展示，但不把整份保单归为寿险产品，也不据此直接认定已经配置独立寿险兜底。若经济责任人有被抚养人或家庭债务，但档案中未查到已核实、当前有效的寿险类产品，应提示优先核对家庭兜底安排，并一并核对其他保单的附带身故责任。

同时区分寿险的两类价值：一是合同约定的身故/全残等保障责任，二是现金价值、保单账户或分红等长期资金属性。增额终身寿和分红型产品仍进入寿险保障清单，但应分别展示当前合同保证的身故利益、保额递增规则、现金价值，以及非保证分红或演示利益；不能把未来演示值当成当前已拥有的家庭兜底金额，也不能把现金价值与身故保额相加成一个总保障额。

有家庭收入、负债和责任期限等资料后，可辅助整理家庭责任资金的测算因素，例如未偿负债、家庭必要支出、抚养年限和可动用资产；任一关键数据缺失时只列待补信息，不输出看似精确的目标保额。已有身故责任要按被保险人、受益安排（如已核实）、保障期限、当前保证金额及金额变化规则分别展示；不默认不同责任能够重复叠加赔付。

### 5.4 主线三：年金是否匹配养老、教育等长期现金流目标

年金类产品需要纳入客户的保单整理和展业分析，但作为“未来现金流安排”单独呈现，不视为医疗、重疾或身故风险保额。对每份年金合同核对：

- 领取对象、开始领取时间、领取频率、领取期间和领取条件。
- 合同保证的领取金额/次数，与分红、万能账户结算或其他非保证利益分开列示。
- 当前缴费金额、缴费频率、缴费期限，以及缴费期和领取期是否重叠。
- 若合同含身故责任，单独放入寿险责任清单，并注明具体给付条件；不把年金领取总额、现金价值和身故保险金合成一个数字。

结合客户已说明的养老、教育或其他长期现金流目标，判断是否需要进一步了解现有收入来源、目标开始时间和可承受缴费。如果目标或预算未提供，提示补问，不判断“年金配置不足”，也不依据演示利益承诺未来收益。对应的服务与展业建议可以是整理领取时间表、核实保证与非保证利益、讨论客户希望补充的长期现金流目标。

### 5.5 分险种呈现，不用单一总额

- **医疗：** 单独整理年度/终身限额、免赔额、报销范围与比例、医保结算要求等；不把医疗额度与给付型保额相加。
- **重疾：** 整理确诊/疾病条件、给付金额及多次给付等条件；与医疗报销分开看。
- **寿险/身故：** 寿险产品纳入定期寿险、终身寿险、增额终身寿和分红型寿险；其他险种附带的身故给付作为责任单独列出，避免将整份重疾险、意外险或医疗险误分类为寿险。分别整理当前保证身故责任、保障期限、保额递增规则、现金价值和非保证利益。结合家庭经济责任、负债和被抚养人信息识别兜底问题；无收入/负债资料时不估算目标保额。
- **意外：** 将意外身故、伤残和医疗/津贴拆开展示，结合职业风险和责任范围核对。
- **年金：** 单独呈现缴费与领取现金流、保证领取利益和非保证利益，并结合养老/教育等目标核对；不作为医疗、重疾或身故保障额度。
- **寿险的长期资金属性、财产险：** 寿险的现金价值和非保证分红单独作为长期资金信息展示，不并入身故保障金额；财产险也独立查看，不当作人身风险保障额度。

每条建议都应支持业务员拿来服务客户：

- **客户问题：** 例如“目前看到了住院费用保障，但续保条件还没核实；是否还有单位补充医疗或其他医疗险？”
- **资料动作：** 请客户补充医保/单位福利信息、保单首页、责任页或有效状态证明。
- **沟通重点：** 解释当前已有什么、哪些条件还不清楚、家庭经济责任人身故后会影响谁。
- **展业方向：** 根据已确认的缺口标注“可进一步讨论医疗费用补充 / 重疾现金支持 / 家庭责任兜底”等保障方向，并记录优先级、预算意愿和约定回访日期。

系统区分“保障问题提示”与“产品建议”。第一版可以帮助业务员发现并跟进需求机会；具体产品推荐和投保方案须在核实客户需求、预算、产品适用条件及正式资料后由业务员另行判断。

## 6. 分阶段实施

| 阶段 | 交付 | 关键验收点 |
| --- | --- | --- |
| 0. 口径与数据字典 | 确认保障分类、金额口径、缴费频率、核实状态和展示用语 | 每类保障的数值是否可汇总有明确规则；不能汇总时明确并列展示 |
| 1. 多保单结构化与人工核对 | 新增保障责任明细、保费结构字段和来源定位；合同整理结果可编辑并保存为待核实 | 多份合同可以分别整理；AI 抽取未经人工确认不进入“已核实汇总” |
| 2. 客户保障概览 | 在客户详情聚合多份保单，按被保险人、保障类型和状态展示；汇总年交保费 | 有效、待核对、失效记录分开；医疗限额、重疾保额、寿险保额等不混加 |
| 3. 客户情况与三条主线初筛 | 收集医保/单位福利、家庭经济责任/负债，以及养老、教育等长期现金流目标；分别检查医疗保障、家庭身故兜底和年金安排 | 没有关键资料时显示“待确认”；不把未录入说成无保障或缺口，不把年金目标与风险保额混算 |
| 4. 客户服务与展业跟进 | 为每个保障问题生成沟通问题、资料清单和可讨论的保障方向；记录预算意愿、客户反馈和跟进日期 | 建议指向真实资料与客户情况；不自动生成投保/退保操作或具体产品结论 |
| 5. 家庭扩展与质量迭代 | 复用家庭成员/被保险人关系做家庭总览，支持不同成员的需求和责任 | 家庭保单去重；跨成员保单不串档；成员数据缺失单独提示 |

建议先完成阶段 0—2，尽早让多份保单从“分散合同”变成“可核对的保障概览”；再推进阶段 3—4。这样可以先解决保单多、信息散和无法汇总的问题，同时避免在基础数据不可靠时直接给建议。

## 7. 页面和代码落点建议

- 前端延续客户详情内的 `PolicyContractOrganizer` 与现有保单卡片，新增独立的客户保障概览/初筛 feature 组件；不继续把整个分析流程堆进 `App.jsx`。
- 纯汇总与规则判断放在独立 JavaScript 模块，便于用固定输入验证状态过滤、金额口径和边界文案。
- 后端把合同解析、保单保存、保障明细核对和客户保障概览分别放到对应领域操作中；API 路由与 `api.js` 同步维护。
- 数据库采用可重复执行的版本迁移；保留结构化字段的来源、核实状态和合同责任定位。不要把原始 PDF 全文或重复的合同摘要复制到客户档案。
- 模型只处理单合同已筛选片段；汇总和规则初筛不产生额外模型 token 消耗。若后续使用模型润色建议，输入只包含已确认的结构化摘要，并受用户授权控制。

## 8. 验收场景

1. 同一被保险人有多份医疗、重疾、寿险保单：概览能分险种列出责任、各自口径及合同来源；只对可比且已核实的项目汇总。
2. 保单由家长投保、孩子被保险：孩子的保障归到孩子名下，不记到投保人保障中。
3. 同一客户有一份已核实有效、一份待核实、一份已失效：三种状态分组展示，后两份不污染当前保障合计。
4. 一份合同有多个责任：逐责任整理，不把不同保障金额合为一个“总保额”。
5. 保费为月缴、年缴、趸交和频率不明：只按可确认的口径展示；不明项提示核实。
6. 未提供收入、负债或家庭责任：相关缺口显示“资料不足，无法初筛”，并列出需要补问的信息，不生成目标保额。
7. 客户主要收入承担者有被抚养人或房贷，但没有已核实身故责任：提示优先沟通家庭兜底安排，列出测算所需的负债、家庭支出和责任期限资料。
8. 客户已有增额终身寿或分红型终身寿：纳入寿险责任清单，同时分开展示合同保证的身故利益、保额变化规则、现金价值和非保证利益，不把演示分红当作确定保障。
9. 客户已有年金产品：按合同列出缴费与领取时间表，区分保证领取与非保证利益；若客户尚未说明养老/教育等目标，列为待沟通，不评价配置不足。
10. 有已确认的医疗保障需求但当前档案未查到相应费用补偿责任：提示先确认医保、单位福利和系统外商业保单，再决定是否需要进一步讨论医疗费用保障。
11. 初筛建议可以转成“联系客户补医保/保单资料”“预约家庭保障检视”或“整理年金领取计划”等跟进事项；不自动创建具体产品投保任务。

## 9. 明确不纳入首版

- 自动判定“保障充足/不足”的统一分数或未经确认的行业标准保额。
- 自动购买、退保、替换、理赔结论或个性化产品推荐。
- 让 AI 对多份完整合同做一次性长上下文比较。
- 把家庭成员关系、同姓或合同中的名字自动认定为投保/被保险关系。
- 将年金、账户价值、医疗报销限额、疾病给付、身故保额合并为单一总额。

## 10. 后续产品决策

首版从客户详情的“保障检视”开始，缺口判断优先按**当前客户本人**展示，避免把投保人和被保险人混为一谈。后续再复用家庭成员关系汇总不同家庭成员的保障与需求。

## 11. 当前实现与后续迭代

### 当前实现

- `src/features/customers/CoverageReviewPanel.jsx`：客户保障检视、服务提醒、家庭情况表单与摘要导出；保障明细前增加年交保费与保障金额汇总，明细展示合同摘要和给付条件。
- `src/features/customers/coverage-review.js`：保障分类、状态过滤、保费识别、缺口初筛、明细摘要与 HTML 摘要生成；保额数字与保单状态分开汇总，未能自动归类的合同权益保留在产品所属类别。
- `src/features/customers/coverage-review.css`、`src/styles/shared.css`、`src/styles/theme-dark.css`：保障汇总布局、系统级提示框样式及亮色/暗色主题。
- `backend/customer-coverage-operations.js`、`backend/migrations/016_customer_coverage_profiles.sql`：客户保障情况保存与只返回必要汇总数据的接口。
- `policies.basic_sum_insured` 保存从合同明确字段提取的基本保险金额；保障检视区分“资料已核实”和“合同状态待确认”，未知在保状态仍不会被计入有效保障。
- `PolicyContractOrganizer` 增加投保人和被保险人录入项；分析不会仅凭合同姓名自动归属保障对象。

### 展示层级

- 客户详情先显示保障检视：档案状态与服务建议优先；关键金额只在汇总区出现一次，避免顶部指标与分类卡片重复报数。
- 分类明细按“保障类型 → 被保险人 → 单份保单”展开。折叠行只显示产品、状态、保费和已识别基本保额；展开单份保单后查看责任金额、给付方式、合同页码和疾病定义。
- 合同整理只负责单份合同的上传、AI 结果核对与归档。归档后的完整抽取结果默认收起；统一保障明细以保障检视为准。
- 保单档案默认收起，集中提供状态核实、服务记录和删除等维护操作，避免重复铺开已在保障检视中展示的责任摘要。
- HTML 摘要沿用“关键汇总 → 分类型明细 → 服务建议”结构；不重复输出一份类别概览和一份相同的保单总表。无法归类的保单单列提示。

### 目前口径与限制

- 医疗、重疾、意外、寿险、年金分开查看，不合并成单一“总保额”。增额终身寿和分红型寿险归入寿险记录；年金作为未来现金流单独呈现。
- 医疗合同中住院医疗与住院前后门急诊若按同一一般医疗费用限额计算，保障检视只汇总展示一次共享年度限额；合同整理明细在两项责任旁标注共享限额，避免误认为没有金额或存在额外额度。只有理赔办理说明、没有独立给付金额的“相关保险金”不作为独立保障责任展示。
- “档案未查到”只代表工作台当前记录中没有，不等于客户现实中没有。
- 个人初筛按被保险人姓名与客户姓名精确匹配。未填写被保险人的保单可以在分类明细中看到，但不会被归到客户本人名下；家庭成员级初筛尚未实现。
- 年交保费仅识别少数明确写出年缴/月缴频率的文本。识别不确定的保费不计入合计，并显示待核对数量；趸交等复杂缴费方式暂不自动年化。
- 汇总区分别显示“已核实有效年交保费”和“待核对记录中可识别的年交金额”，并提供含待核记录的档案识别合计；该合计不等于客户当前确定支出。重疾基本保额先显示可识别金额合计，再拆分已确认有效与待核金额，避免因保单状态待核而隐藏合同中已识别的金额。
- 不生成跨险种的单一总保额。医疗年度限额、重疾基本保额、意外/身故责任和年金现金流计算方式不同，且可能共享限额或按条件给付；除可确认的重疾基本保额小计外，其他责任按保单分别展示，避免重复或错误相加。
- 已整理合同中的责任摘要可以辅助分类，但完整条款、重复责任能否叠加、续保条件和非保证利益仍需对照合同人工核实。
- 导出为独立 HTML，适合保存或打印成 PDF；目前不是可继续编辑的 Excel/Word 表格，也不会把 PDF 原件嵌入摘要。

### 下一步建议

1. 支持按家庭成员逐人补充医保、收入责任、依赖人数、债务和长期目标，并在家庭页按成员显示服务重点。
2. 增加保障责任逐项核对/修改，让业务员确认分类、保额口径、给付方式、起止时间、保证与非保证利益及责任来源。
3. 扩充缴费频率识别和趸交/不规则缴费呈现，继续坚持“不能可靠换算就不相加”。
4. 在业务员确认责任后，再评估增强导出格式和字段：PDF 客户摘要、Excel 保单明细或打印版家庭检视表。
5. 根据实际客户使用反馈校准提醒规则；在验证前不引入统一保额标准、评分或自动产品推荐。
