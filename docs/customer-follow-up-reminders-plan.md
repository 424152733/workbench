# 客户待办与工作台内提醒增强实施计划

**版本：** 0.1（待评审）  
**状态：** 仅完成方案，尚未实施  
**范围：** 客户与保单模块中的客户跟进待办，以及工作台首页、客户详情和通知入口  
**目标用户：** 当前工作台的单人保险代理人

## 1. 目标与已确认边界

首要目标是避免漏掉客户跟进。代理人应能清楚看到逾期、今日和接下来需要联系的客户，完成一次联系后留下结果并安排下一次跟进。线下拜访、转介绍和内容渠道客户使用同一套待办流程，内容关联仍为可选项。

本轮仅做**工作台内提醒**：首页、客户与保单页面、客户详情及顶部通知。页面关闭时不会弹出电脑通知，也不发送短信、微信或邮件；因此本轮的提醒依赖代理人打开工作台。保单缴费、续保、理赔等服务事项可在后续独立规划，本轮先聚焦客户联系待办。

一期需求稿已提出“首页和客户详情显示今日/逾期待办；可完成、延期；避免同一事项重复提醒”。本方案将这些要求落成明确的数据与交互规则。

## 2. 当前实现与问题

| 位置 | 当前行为 | 本轮需要解决的点 |
| --- | --- | --- |
| 新增客户 | 可选“下次跟进”，后端将它写入一条 `follow_ups` 记录 | 安排未来事项被写成了已经发生的沟通记录；改为直接创建待办 |
| 记录跟进 | 保存沟通摘要，可选 `next_followup` 日期 | 历史记录与未来待办混在一起，缺少完成、延期、取消状态 |
| 客户详情/列表 | 从历史记录中取一条非空 `next_followup` 显示 | 旧日期可能长期保留；应显示最早的未完成待办 |
| 首页/通知 | 从历史记录中找未来 7 天内日期，每位客户最多显示一项 | 不能区分逾期和今日，也不能从通知直接完成或延期；顶部角标可能长期亮着 |
| 数据库 | `follow_ups` 表只有 `next_followup DATE` | 需要单独的待办实体和状态变更记录 |

参考实现：`backend/schema.sql`、`backend/workbench.service.js`、`backend/api.controller.js`、`src/App.jsx`、`src/api.js`。

## 3. 用户操作流程

### 3.1 安排待办

1. 新增客户时，填写“下次跟进”会创建一项待办，不再创建一条虚构的沟通记录。
2. 在客户详情的“跟进待办”区域可以新增待办。填写联系目的、日期、可选时间、计划联系方式和备注。
3. 记录一次实际沟通时，可以同时安排下次跟进；两条数据在同一事务内保存，避免只保存了沟通记录却漏掉提醒。
4. 同一客户允许有多项不同的待办，但新建时提示同日、同目的的现有未完成事项，避免误操作导致重复提醒。重复提交由前端禁用按钮及后端幂等约束共同处理。

### 3.2 查看提醒

- **工作首页：** 将待办分为“已逾期”“今天”“未来 7 天”，逾期排在最前。显示客户、事项、计划方式、日期/时间，提供“完成并记录”“延期”和“查看客户”。首页只展示少量事项，提供“查看全部”进入完整列表。
- **客户与保单：** 增加“跟进待办”视图，支持逾期、今天、未来 7 天、全部未完成和已完成筛选；搜索客户姓名或事项。客户列表保留“下次跟进”列，显示该客户最早的一项未完成待办。
- **客户详情：** 在沟通时间线前显示该客户的未完成待办，并可新增、完成、延期或取消；历史沟通与待办变更记录分开显示。
- **顶部通知：** 角标仅统计今日和逾期的客户跟进事项，以及现有待审核内容。打开通知可直达待办；点击查看不会把未完成事项当作已处理。未来 7 天事项可在通知面板的“即将到期”区域查看，但不让角标一直亮着。

页面初次进入、重新获得焦点、执行待办操作后刷新提醒；页面可见时定期刷新一次，建议每 60 秒。跨过本地日期边界后重新计算“今天”和“逾期”。接口失败时保留已加载内容并提示刷新失败，不把任务误显示为已完成。

### 3.3 完成与延期

| 操作 | 规则 |
| --- | --- |
| 完成并记录 | 必填本次结果或简短摘要，选择实际沟通方式；保存沟通记录、完成待办、更新客户最近联系时间。可同时安排新的待办 |
| 未接通 | 也算完成本次联系尝试；结果写为“未接通”，可顺手安排重试日期 |
| 延期 | 快捷选择明天、3 天后，或自选日期/时间；原计划和改期原因写入待办变更记录。延期后旧日期不再触发提醒 |
| 取消 | 用于客户不再需要该事项等情形；要求简短原因，保留可追溯记录；取消后不再提醒 |
| 重复点击或多窗口操作 | 后端仅允许未完成待办发生状态变更；已处理事项再次提交返回明确冲突，前端刷新最新状态 |

联系授权状态变为“已拒绝联系”时，现有未完成的客户联系待办自动取消并记录原因，且禁止新建此类待办。之后若状态改变，不自动恢复旧待办，由代理人重新安排。“待确认联系偏好”的客户仍可保存用于确认联系安排的待办，界面显著提示先核对联系意愿。

## 4. 数据设计

新增 `customer_follow_up_tasks`，只保存尚未发生或已处理的跟进事项；`follow_ups` 继续保存真实发生的沟通历史。

| 字段 | 说明 |
| --- | --- |
| `id`、`customer_id` | 主键；客户外键使用 `ON DELETE CASCADE`，客户删除时待办及事件一并删除 |
| `title`、`method`、`note` | 联系目的必填；计划联系方式和补充说明可选；限制长度，避免把完整敏感材料写入待办标题 |
| `due_date DATE`、`due_time TIME NULL` | 日期必填，时间可选；仅填日期时当天全天属于“今天”，次日才转为逾期 |
| `status` | `pending`、`completed`、`cancelled`；不单设“已延期”，延期仍为未完成状态 |
| `source` | `manual`、`customer_create`、`follow_up`、`legacy_migration`，用于区分来源 |
| `source_follow_up_id` | 可选关联历史沟通记录；唯一约束用于旧数据迁移和一次沟通安排一次待办的幂等控制 |
| `request_key` | 可选的客户端请求标识，唯一约束用于抵御新建请求重发；同一个标识重试返回原待办 |
| `completed_follow_up_id`、`completed_at` | 完成时关联实际沟通记录，并记录完成时间 |
| `created_at`、`updated_at` | 审计和排序 |

另建 `customer_follow_up_task_events`，记录创建、改期、完成、取消的动作、时间、改前/改后日期及原因，关联待办并使用 `ON DELETE CASCADE`。对待办建立 `(status, due_date, due_time)` 和 `(customer_id, status, due_date)` 索引。状态和值范围由数据库约束及服务端共同校验。

本轮以 `Asia/Shanghai` 作为业务日期和时间的计算时区，前后端都使用明确的日期字符串；不依赖数据库服务器的默认时区。`due_time` 只影响当天的排序和展示，不会让当天事项提前变成“逾期”。

### 4.1 旧数据迁移

数据库初始化目前会在 API 每次启动时运行 `backend/schema.sql`，因此建表和回填都必须可重复执行。

1. 保留已有 `follow_ups` 沟通历史，不删除、不改写原始记录。
2. 每位未拒绝联系的客户，从有 `next_followup` 的历史记录中取**最近创建的一条**，迁入最多一项未完成待办；标记“旧提醒迁入，建议核对”。这样保留目前页面显示的下一次跟进，同时提醒代理人核对可能过期的旧日期。
3. 回填 SQL 放在示例沟通记录写入之后；通过 `source_follow_up_id` 唯一约束保证重启后不会重复迁入。完成或取消迁入事项后，重启也不能让它重新出现。
4. 新版本中，新增客户的预约直接写待办；记录沟通并安排下次跟进时，历史记录和新待办在同一事务内写入并关联，避免回填再次生成重复事项。
5. 迁移前后核对客户数、迁入待办数及逾期数；对未迁入的旧记录保持可查，避免静默丢失历史。

## 5. 接口与业务规则

| 接口 | 用途 |
| --- | --- |
| `GET /api/follow-up-tasks` | 按状态、时间范围、客户和搜索词分页查询；服务端排序为逾期、今天、近期、其余 |
| `POST /api/customers/:id/follow-up-tasks` | 为客户创建待办；校验日期、联系状态、字段长度及重复提交标识 |
| `PATCH /api/follow-up-tasks/:id` | 修改联系目的、计划方式、备注或日期；日期变更写事件 |
| `POST /api/follow-up-tasks/:id/complete` | 完成待办，写实际沟通记录，可同时创建下一项待办；原子事务 |
| `POST /api/follow-up-tasks/:id/cancel` | 取消待办并记录原因 |
| 现有 `POST /api/customers/:id/followups` | 保留直接记录沟通的能力；提交 `next` 时同步创建下一项待办 |
| 现有 `GET /api/dashboard`、`GET /api/notifications` | 从新待办表统计和展示，不再从历史 `next_followup` 推断未完成任务 |

首页指标明确区分：`overdueTasks` 为早于今天的未完成项，`todayTasks` 为今天的未完成项，`upcoming7Tasks` 为明天至第 7 天的未完成项。客户数与待办数分别标注；若一个客户有两项待办，待办列表显示两项，不误称“两位客户”。现有 `dueFollowUps` 可在兼容期保留，但前端改用含义明确的新字段。

客户详情返回该客户待办摘要和最早未完成日期。列表接口避免为每位客户逐条查询，使用聚合查询或批量查询；完成、延期、取消后统一刷新客户详情、首页统计及通知角标。所有会提交接口的按钮均有加载状态并防止重复提交。

新建接口接收前端生成的 `requestKey`。若网络超时后用相同标识重试，返回已创建的待办。完成接口在事务内锁定待办行，确认状态仍为 `pending` 后再写沟通记录和下一项待办，避免重复点击生成两条沟通记录。

## 6. 页面与交互改动位置

- `src/App.jsx`：首页待办卡片、客户与保单中的待办视图、客户详情待办区、完成/延期/取消弹层、顶部通知角标与入口。
- `src/api.js`：新增待办请求；旧记录跟进接口保持兼容。
- `src/styles.css`：逾期/今日/近期状态、窄屏布局、明亮/黑暗主题样式。
- `backend/api.controller.js`：待办路由和请求参数接入。
- `backend/workbench.service.js`：列表、校验、事务、指标与通知数据。
- `backend/schema.sql`：可重复执行的建表、索引和迁移 SQL。

已有菜单路由继续同步地址栏；新增的客户模块视图可用查询参数保存筛选，以便刷新后仍回到之前的待办视图。若实现时发现与现有路由约定冲突，优先保持客户模块当前路由可正常刷新。

## 7. 验收场景

1. 新建线下客户并设置下次跟进：客户详情与待办列表各出现一项待办；沟通时间线不出现虚构的“初次联系”记录。
2. 今天、昨天、7 天内及 8 天后的任务进入正确分组；只填日期的事项全天保持“今天”。
3. 同一客户两项不同待办都可见；客户列表显示最早未完成日期，指标分别统计待办数和客户数。
4. 完成待办时记录“已联系”或“未接通”及实际方式，历史时间线增加一条真实沟通，原待办从未完成列表和通知角标消失；同时安排的下一项待办出现。
5. 延期后旧日期不再提醒，事件历史能看到改期前后日期和原因；取消后同样不再提醒。
6. 将客户标为“已拒绝联系”后，待办取消且不能再新增客户联系待办；改回其他状态不会恢复旧任务。
7. 刷新页面、切换菜单或重新启动 API 后，待办与状态不丢失、不重复；旧 `follow_ups` 最多迁入每位客户一项，已完成的迁入事项不会复活。
8. 顶部角标只因今日/逾期跟进或待审核内容亮起；点击通知并未完成事项时角标仍保持。工作台内数据在窗口重新获得焦点后更新。
9. 窄屏和黑暗主题下可以完整查看、完成、延期待办；接口失败时按钮停止加载并提示原因，原待办状态保持不变。
10. 删除客户时，关联待办和事件随客户删除，不留下孤立记录。

## 8. 验证与实施顺序

1. **数据层：** 新表、索引、幂等回填；用可丢弃数据库重复启动，检查回填数量和历史数据保留。
2. **服务端：** 待办 CRUD/状态转换、完成事务、拒绝联系规则、看板及通知统计。用 HTTP + PostgreSQL 集成测试覆盖验收场景中关键状态变化和重复提交。
3. **前端：** 首页、客户详情、完整待办视图、通知角标与刷新机制；先接真实本地 API，再检查加载和错误状态。
4. **验证：** 运行 API 测试、现有 UI 逻辑测试及构建；在浏览器实际走新建、逾期、完成、延期、取消、刷新、窄屏和黑暗主题流程。最后补一份测试报告，说明通过项及剩余问题。

测试不得连接实际客户数据库，也不调用 Runware 或其他付费模型；本功能只处理本地业务数据。

## 9. 评审时需要确认的默认选择

以下按推荐方案写入，评审时可以调整：

1. 日期必填、具体时间可选；未填时间的任务按“当天”提醒，不设默认的 09:00 截止时间。
2. 一位客户允许多项不同的待办；同日同目的显示重复提醒，由代理人决定是否继续创建。
3. 对旧数据保留每位客户最近一条有日期的提醒，并标注“旧提醒迁入，建议核对”，以减少升级时漏掉原有安排。
4. 工作台内角标只计算今日和逾期客户待办；未来 7 天待办仍可在首页和列表查看。
