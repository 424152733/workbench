# 产品中心：在售产品资料同步实施方案

**版本：** 1.5（友邦产品已完成应用内同步；中国人寿停止接入）

**日期：** 2026-10-20

**适用项目：** 保险顾问工作台

## 1. 目标与范围

将产品中心的主要建档方式改为“选择保险公司 → 同步该公司官网当前在售产品 → 查看官方资料和来源”。首批支持新华保险、友邦人寿、泰康人寿、平安人寿和太平洋人寿。用户维护要同步的公司，并可对一家或全部已启用公司发起同步。

**核心准入规则：只有保险公司官方披露页面明确标为“在售”，或位于明确命名的“在售产品”目录中的产品，才可进入同步后的在售产品库。** 搜到产品条款、备案记录、官网宣传页或较新的 PDF，均不能单独证明它仍在售。停售、历史版本和状态无法确认的产品不得作为在售产品导入，也不下载其停售资料。

首期同步个人保险主险和适用的附加险，排除团体保险、组合计划中无法识别为独立在售产品的条目。产品是否在保险公司官网列为在售，与当前代理渠道、地区是否可销售是两件事；界面单独显示“渠道可售情况未核实”，不据此作销售承诺。

本方案聚焦在售产品及其官方材料的获取、更新与溯源。本期不建设产品对比、自动报价、收益测算或自动发布功能。现有手动上传保留为在售产品的补充资料入口，上传件必须显著标为“人工补充”，不能冒充官方同步文件。

## 2. 现状与需要调整的边界

现有 [产品中心规划](./product-center-plan.md) 和 [实施记录](./product-center-implementation-report.md) 以手动创建产品、上传 PDF/DOCX/TXT、人工确认 AI 提取结果为主。当前数据库已有公司字典、产品、资料、提取结果、文案草稿及版本；产品的“整理中/可用/已停用”属于**工作台内部编辑状态**，不能作为官网销售状态。前端页面、接口和服务分别位于：

- 前端：src/features/products/ProductCenterPage.jsx、useProductCenterWorkspace.js、products.css，接口封装在 src/api.js。
- 后端：backend/api.controller.js、workbench.service.js、product-center-operations.js。
- 数据：backend/migrations/002_product_center.sql 及后续版本化迁移。

重构应保留已录入的产品、资料、提取结果和草稿；不得根据名称自动把旧手动档案并入官网档案。人工确认同一产品后才建立关联。已确认提取结果及文案继续指向生成时使用的资料版本，官网文件更新不覆盖旧引用。

| 再后续外资/合资寿险 | 中意人寿、中英人寿、中信保诚人寿、招商信诺人寿 | 可先验证[中意在售产品材料](https://www.generalichina.com/gexianzaishou/index.html)和[中英在售产品信息](https://www.aviva-cofco.com.cn/website/xxzx/gkxxpl/gsjbxx/grbxcpxx/zscpxx/list-1.shtml)的采集方式，再决定开发次序。 |

以上是**公司接入候选**，不是待同步的产品清单，也不是承诺这些公司均可一键获取。优先级综合业务覆盖与官网在售证据的可取得性，不代表保费规模或产品质量排名。养老保险公司可在用户需要个人养老金等产品时另立专项范围；再保险、财险和名称含“在线”但牌照属于财险的公司不纳入本方案。

每增加一家公司的固定步骤为：确认法律主体和官网域名 → 找到当前在售目录及全部分类 → 验证分页、产品稳定键和官方材料 → 固定公开样例与排除规则 → 开发适配器 → 通过在售过滤及失败回退验收 → 将“待接入”改为“可同步”。缺少明确在售证据或材料访问受限时，停留在“待接入/暂不可同步”，不使用旧清单补足数量。

## 4. 用户流程与界面

### 公司管理

- 预置首批五家公司（新华、友邦、泰康、平安、太平洋），并可展示后续候选公司的“待接入”状态；显示同步能力、启用状态、最近成功核验时间、上次结果。用户可启用或停用已支持公司，点击“同步在售产品”或“同步全部已启用公司”。
- “添加公司”只创建待接入配置。没有对应采集适配器时展示“待接入”，不显示可以一键同步的假按钮。新增公司须完成来源确认、适配器和测试。
- 同步按钮提供运行中状态、防重复点击、阶段进度及清晰错误；同一家公司同时只允许一个任务运行。

### 在售产品库

- 默认只列出最近一次**成功核验为在售**且仍在有效期内的官网产品。支持公司、险种、主险/附加险、资料完整度筛选及搜索；不加入横向对比界面。
- 每行显示产品名称、官方代码或备案号（若有）、官网在售状态、来源链接、最近核验时间、资料数量与缺失项。
- 产品详情展示官方页面链接、条款、费率表、产品说明/说明书、现金价值表等实际可取得的资料；对缺失资料显示“官网未提供/获取失败/待复核”，不把空白解释成不存在。
- 官网状态过期或抓取异常时显示“待复核”，从默认在售选择器移除，避免旧数据继续被当作当前在售。可在管理视图查看历史档案和同步异常。
- 既有手动档案继续可查看；未核实官网在售状态的档案不进入默认在售选择器。用户可人工关联并核对官方产品身份。

### 同步结果

每次任务显示按公司统计的在售发现数、成功入库数、新增数、资料更新数、资料缺失数、排除的团体/停售/未知数，以及失败原因。显示源页面、开始/结束时间和下一次建议复核时间。允许对失败公司重试，不重复导入成功公司。

## 5. 数据模型与迁移

使用新的版本化迁移；实施时按仓库现有迁移编号选下一个可用编号，不在启动初始化 SQL 中覆盖用户数据。

| 对象 | 新增或调整字段 | 约束与用途 |
| --- | --- | --- |
| product_company_dictionary | 首批五家公司代码与名称、是否启用；后续候选可新增为未启用，适配器能力由服务端固定注册 | 用户启用公司不等于该公司已有适配器。停用公司仅从活动公司选择器移除，历史产品和同步记录保留。不同法律主体不得合并公司代码。 |
| insurance_products | 来源类型（official_sync/manual）、官方产品 ID/代码、官方页面 URL、官网销售状态、状态证据 URL、最近核验时间、主险/附加险/团体分类、同步批次 ID | 内部编辑状态保持独立；官方 ID 存在时按“公司＋官方 ID”去重。无 ID 时以经过验证的官方页面标识构造稳定键，不仅凭名称合并。 |
| product_official_materials | 当前官方资料类型、标签、文件 URL、在售来源页、当前版本标记、首次/最近发现时间 | 全目录同步只保存官网提供的链接，不批量下载数千份附件；用户从产品详情选择单份资料导入后，文件存入 `product_documents` 并记录来源 URL 与 SHA-256。 |
| product_documents | 来源类型、官方文件 URL、源页面 URL、文件类型、SHA-256、取得时间 | 支持费率表、现金价值表等类型。重复导入相同内容时复用已有官方导入记录；不同内容保留为独立资料，供提取结果和稿件溯源。 |
| product_sync_runs | 公司、状态、开始/完成时间、发现/导入/排除/失败计数、错误摘要 | 支持进度查询、重试和审计；状态包括排队、运行中、成功、部分成功、失败。 |
| product_sync_events | 批次、产品键、动作、源链接、原因、时间 | 记录新增、更新、待复核、确认停售和跳过；避免只看最终状态而无法解释变化。 |

销售状态建议为“已核验在售 / 待复核 / 已确认停售”，并记录核验时间和证据。默认在售有效期先设为 **7 天**，作为可配置运行参数；超过有效期但未复核的产品转为“待复核”，不推断其已停售。只有官网明确写明停售，或在官方停售目录中确认该产品，才可标为“已确认停售”。即使停售，历史产品与资料、已生成草稿也应保留在管理视图，默认在售产品库不展示。

数据库唯一键和外键需按现有表关系设计；迁移要可重复执行且不修改既有草稿引用。已有“公司＋名称＋版本”唯一约束与官方 ID 唯一键可能冲突，实施时应先为源产品引入独立映射/关联表或审慎调整约束，再做数据迁移，不能直接覆盖手动产品。

## 6. 后端设计与同步算法

### 分层

- 在 backend/product-sync/ 下为五家公司分别实现适配器。统一接口输出：官方产品键、名称、险种、主附险类型、官网销售状态证据、产品页链接、资料清单与原始页面定位。
- 独立的同步编排领域操作负责锁、分页、下载、校验、入库和任务结果；经 WorkbenchService 复用同一数据库上下文。api.controller.js 只接收参数并返回响应。
- 资料继续接入现有 product_documents 存储与解析流程；同步本身仅做确定性的采集和文件解析，**不调用 GPT、Runware、Humanizer 或图片服务**。用户随后手动发起要点提取、核对和文案生成。

### 单家公司同步步骤

1. 校验公司已启用且适配器可用，为公司取得互斥锁并建立同步批次。重复请求返回正在运行的批次 ID。
2. 读取官网在售目录的全部分页和分类，保留来源 URL、抓取时间、页码及状态原文。校验分页完整性、行数和关键字段；页面结构异常或数量骤降时中止发布本次结果并报警。
3. 只把明确在售、属于个人险范围的条目放入候选集合；团体、停售、历史版本、状态未知的条目记录排除原因。附加险可单独建档，并标注不能单独销售时的关系信息（若官网有依据）。
4. 为每个候选产品解析当期官方文件链接并保存为资料引用，不在公司目录同步时批量下载附件。用户点击单份资料的“导入”后，仅访问经过配置的官网域名与官方静态资源域名；验证 HTTPS、重定向目标、25 MB 上限和 PDF 文件签名，解析后记录 SHA-256。缺少或导入失败的材料逐项显示，产品不因此被补造资料。
5. 产品按官方键幂等入库；资料链接按产品、类型和 URL 幂等更新。导入的官方文件按内容哈希识别重复件；不同内容作为新资料保存。单产品资料元数据在事务中提交，暂存文件在提交失败后清理。保留既有提取结果和稿件引用。
6. 比对本次完整成功的目录与上次结果。仅“从目录消失”不能认定停售，转为待复核；在官网明确确认停售后归档。若本次目录抓取不完整，完全不做批量状态变更。
7. 完成批次并展示结果。单产品失败允许该公司任务标为部分成功；整站失败时保留既有数据，但超过核验有效期的档案不继续出现在默认在售选择器。

同步频率首期由用户手动触发；如将来增加定时任务，应复用同一编排逻辑和互斥锁。请求设置超时、有限重试和退避，控制并发，避免给官网造成高负载；不读取用户登录后的页面，也不抓取个人投保信息。

## 7. API 草案

沿用现有 /api/product-center 前缀、前端 src/api.js 方法和服务门面。

| 方法与路径 | 请求 / 响应重点 |
| --- | --- |
| GET /meta | 公司代码、名称、启用状态、适配范围和最近同步摘要。 |
| PATCH /companies/:code | 启用/停用已支持公司的批量同步；不允许前端提交任意采集 URL。 |
| POST /sync-runs | 传公司代码数组；返回任务 ID 和已在运行的任务信息；校验公司白名单。 |
| GET /sync-runs、GET /sync-runs/:id | 最近同步状态、阶段、计数和结构化错误。 |
| GET /products | 支持官网状态筛选；产品中心默认显示已核验在售档案，可切换待复核和全部档案。 |
| GET /products/:id | 官方来源、销售状态证据、资料链接和本地导入文件；复用现有产品工作区。 |
| POST /products/:id/official-materials/:materialId/import | 从当前官方链接导入单份 PDF，纳入现有资料解析和人工核对流程。 |

同步任务若跨越 HTTP 请求时长，由后端异步运行并在数据库持久化状态；任务重启后可识别未完成批次，避免出现永久“运行中”。所有外部 URL 由服务端适配器产生并经过白名单校验，不能直接拿前端提交的 URL 发起请求。

## 8. 对现有内容流程的影响

- “产品解读”和“客户案例”选择产品时，默认只显示当前已核验在售的官方产品；明确提示来源日期和渠道可售尚未核实。已关联历史产品的旧稿可继续打开和编辑，但新生成前需要重新核对在售状态与资料版本。
- 自动下载的文件先进入“资料待核对”状态。条款、费率、现金价值等细节只有在原文件可追溯且人工确认后才进入可用于生成的产品事实。不得从产品名推断保费、利率、收益或理赔结果。
- 当资料版本变化时，已确认的旧提取结果与草稿标为“资料可能已更新”，用户重新核对后再用于新内容；不自动覆盖现有文案。

## 9. 实施顺序与阶段交付

| 阶段 | 工作 | 完成判据 |
| --- | --- | --- |
| P0：五家来源接入验证 | 分别确认在售目录的分页、分类、唯一产品键、文件链接及访问限制；固定最小公开页面样例，列出全部太平洋在售分类入口。 | 每家公司有一份可复现的字段映射与采集样例，或明确记录无法自动同步的原因；不能把未验证能力显示为可用。 |
| P1：数据与同步内核 | 新迁移、状态/证据模型、幂等入库、文件校验、批次审计和任务锁；以新华适配器贯通端到端。 | 重复同步不重复建档；失败不清空历史；只导入官网确认在售的个人产品。 |
| P2：其余四家公司 | 分别实现友邦、泰康、平安、太平洋适配器与静态页面样例测试。 | 每家公司均能完整遍历其可接入的在售分类，记录排除及缺失资料；官方受限时按“暂不可同步”收口。 |
| P3：界面与内容接入 | 公司管理、同步进度、在售产品库、来源/版本详情、旧手动档案关联、内容选择器联动。 | 用户可一键发起并理解结果；路由刷新、加载、失败、窄屏与明暗主题可用。 |
| P4：按公司扩展 | 按第 3 节的候选顺序逐家做来源验证、适配器、样例测试与上线；专业健康险独立适配。 | 每新增一家都单独通过第 10 节验收；未通过的公司保持待接入，不影响已支持公司的同步。 |

P0 是正式开发五家适配器的准入门槛。若某一家只提供人工访问或下载受限，本期应保持该公司的“暂不可同步”状态，并允许用户手动补充其**已核实在售**产品资料；不能为了达成五家数量而导入无法核实销售状态的材料。

P4 在首批五家同步流程稳定后开展。扩展时复用同步内核、数据结构和界面，仅增加经过验证的公司适配器与来源配置；不把“维护公司名称”误解成任何公司都能自动同步。

## 10. 验收与验证

1. 首批五家公司均在公司列表中；后续候选可显示“待接入”。五家均已配置目录适配器，支持逐家或批量发起同步；官网当次拒绝请求时，应显示同步失败并保留原数据，不能把接入配置等同于官网当前可用。
2. 对官方目录样例逐条验证：**在售个人产品入库，停售、历史版本、团体产品和状态未知条目均不进入默认在售库；其资料不被当期下载。** 分页完整且计数与样例一致。
3. 每个入库产品都可从详情回到官网在售证据页；每份官网资料链接能看到类型和来源，导入的本地文件能看到来源 URL、SHA-256 和取得时间。缺失资料按项说明。
4. 连续运行两次数据不重复；官方文件更新生成新版本，旧提取结果与草稿的来源引用不变。
5. 官网部分失败、页面结构改变或数量骤降时不将产品批量误判为停售。超期产品从默认在售选择器撤下并显示待复核。
6. 已有手动产品、资料和草稿保留；人工关联前不按名称合并。没有官网在售证据的手动产品不进入默认在售库。
7. 同步不触发付费模型、图片生成或自动发布。内容生成仍需要用户操作并核对资料事实。

验证时使用官方公开页面的精简固定样例和假下载器覆盖解析、分页、过滤、重复同步、版本更新与失败回滚；不在测试中依赖实时官网，也不调用付费模型。前端执行构建和相关 UI 逻辑测试。涉及数据库的 API 集成测试仅对一次性、可丢弃的 PostgreSQL 测试库执行，不能使用实际客户数据库。浏览器人工检查产品中心实际流程、刷新后任务状态、窄屏和明暗主题，并如实记录未验证的官网接入项。

## 11. 已知限制

- 官方披露的“在售”可能不等于代理人在某地区、某渠道可销售；渠道资格需另行确认。
- 官网页面结构、下载域名和材料完整度会变化，接入验证通过后仍需要运行监控和适配器维护。
- 官网资料可能没有可机器读取的费率或现金价值；此时只保存原始文件及缺失/解析状态，不自动推算保费、利率或回报率。
