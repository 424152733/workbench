# 家庭规划工作区：关系与保障底座实施计划

**版本：** 1.4（首版实施记录）  
**日期：** 2026-10-17  
**状态：** 核心代码已实现；待一次性数据库迁移验收与真实浏览器流程验收  
**范围：** 客户与保单模块中的家庭规划底座；本次实施范围为家庭关系与保障整理  
**目标用户：** 当前工作台的单人保险代理人

## 1. 目标与已确认的产品约定

从客户独立详情页进入其家庭，在可缩放的关系图上看成员节点与实际确认的关系连线。点击节点可查看此人的信息、保单和服务情况；也可查看家庭财产相关保单及近期保单服务事项。代理人可将客户列表中已有的多条客户记录关联为一个家庭，也可先录入尚未单独建档的家人，日后再关联客户档案。

以下约定已经在需求讨论中确认：

1. **关联不合并客户。** 每位客户仍有自己的来源、阶段、联系授权、跟进历史和保单归属；来自线下和内容渠道的客户可以属于同一家庭。
2. **家庭成员不一定是客户。** 无独立客户档案的家人可以作为简要成员存在；这种成员不计入客户数、线索数或来源统计，也不能直接产生联系待办。
3. **保单按真实角色关联。** `policies.customer_id` 继续表示当前工作台中管理这份保单的客户档案；投保人、被保险人和车辆/房屋等保障对象在家庭视图中另外明确关联。家庭成员关系本身不会改变合同角色。
4. **人工确认关系与归属。** 不按同姓、电话或保单中相似的姓名自动建立家庭关系，也不自动推断某份保单的保障对象。
5. **客户详情使用独立路由页面。** 客户列表、首页待办和家庭成员节点均可进入同一客户详情；面包屑提供明确的返回路径。

### 1.1 最终业务目标与本次交付

**最终目标：** 以家庭为单位，帮助代理人与客户共同梳理家庭成员、财产、负债、收支、已有保障、主要风险和生活目标，在可核实的资料与明确假设上比较规划方案，持续跟进变化。家庭关系图是进入资料的导航，保单整理是其中一部分；最终使用者需要看到的是“家庭现状—风险与目标—可选行动—后续跟进”的连续工作区。

本计划的**本次交付范围**仍是成员关系、客户独立详情、保单角色与投保对象整理，以及相关服务事项。它为后续规划提供可追溯的人员、保单和对象关联，尚不交付家庭资产负债表、现金流分析或规划建议。页面命名和数据结构应按“家庭规划工作区”预留扩展，不把关系图或保单数量当成家庭财务全貌。

| 阶段 | 用户得到的能力 | 与前一阶段的数据衔接 |
| --- | --- | --- |
| 本次：家庭关系与保障底座 | 关联成员、确认关系与保单角色；查看已有保单、房屋/车辆等投保对象和服务事项；标记资料待核对 | 保留独立客户与保单记录，建立稳定的家庭成员、保单和投保对象 ID |
| 后续：家庭财务现状 | 经客户确认后记录资产、负债、收入、支出、家庭财务角色与目标；展示有日期和资料完整度的家庭概况 | 资产台账与投保对象明确关联，但两者分开记录；成员属于家庭不等于资产共同所有 |
| 后续独立迭代：投资持仓与估值接入 | 在人工台账可用后，逐步接入投资账户/持仓、估值更新与资料核对；保留客户手工修正和断开数据源的能力 | 统一接入层把外部数据转换为家庭财务资料，保留来源、时间和历史；风险分析不依赖此项先完成 |
| 后续：风险与保障分析 | 围绕成员、资产和目标整理收入中断、医疗支出、财产损失、责任等风险；把已核实保障映射到风险 | 只使用已核实的保单责任与金额做数值分析；缺失资料显示“待补充”，不自动判定无保障或缺口 |
| 后续：多方案规划与跟进 | 基于同一版家庭资料比较不同方案、记录假设与取舍，并交给未来“智能计划书”模块生成可审阅方案 | 方案引用带日期的家庭资料快照；后续资料变化不会悄悄改写已交付方案 |

**最终能力的验收门槛：** 对一个家庭，代理人应能基于同一统计日期查看成员和经济依赖关系、资产负债与收支概况、已核实保障及资料缺口；逐项记录主要风险和目标；在相同资料基础上比较至少两套方案的预算、假设与取舍；把客户确认的行动转为后续跟进，并在家庭情况变化时复盘。缺少财务现状或风险与方案比较时，只能称为“关系与保障整理”，不能标记为已完成家庭规划。

这个分阶段方向参考了 [CFP Board 对财务规划范围的说明](https://www.cfp.net/ethics/compliance-resources/2020/01/financial-planning-and-application-of-the-practice-standards-for-the-financial-planning-process)与 [FPSB 全球财务规划标准](https://www.fpsb.org/wp-content/uploads/2023/04/230000_pub_FPSB-Global-Financial-Planning-Standards-Final.pdf)中对目标、资产负债、现金流和风险的综合分析框架；它们仅作为产品结构参考，不作为本项目适用法规或执业资格的判断。

首版是资料整理与服务视图，不做自动投保建议、理赔判断或“保障缺口评分”。“未录入资料”只说明工作台没有相应记录，不能表述成“没有保险”。

## 3. 业务对象与关联规则

| 对象 | 含义与关键规则 |
| --- | --- |
| 家庭档案 | 一组供保障整理使用的成员，设名称和一位已建档的主要服务联系人；它不是法律上的户籍或婚姻判断。 |
| 家庭成员 | 关联已有客户，或仅记录称呼的简要成员。每位成员在关系图中对应一个节点；主要服务联系人是业务角色，不决定其他成员之间的亲属关系。 |
| 成员关系 | 两个成员之间经过人工确认的连线。首版支持配偶/伴侣、父母与子女、兄弟姐妹、其他关系；亲子关系记录明确方向，其他自定义关系可记录简短说明。未确认关系的成员保留为无连线节点。 |
| 客户成员关联 | 同一客户在同一家庭只能出现一次。建议允许客户属于多个家庭，例如成年子女同时出现在原生家庭与自己的家庭；每个家庭的保单纳入动作独立完成。 |
| 家庭投保对象 | 首版记录车辆、房屋/家庭财产、其他财产的简短名称，用于定位财险保单实际保障对象；不记录估值、产权或负债，不等同于未来家庭资产台账，也不进入客户统计。 |
| 家庭保单 | 引用现有 `policies` 记录，不复制保单。可关联一位或多位投保人/被保险人，以及零个或多个投保对象；同一家庭汇总保单数时按保单 ID 去重。 |
| 保单展示分类 | 为视图人工勾选医疗、重疾、寿险、意外、车险、家财险、其他等标签；一份综合保单可有多个标签。标签只帮助整理，不能代替合同责任。 |

一份保单只有在其管理客户已经加入该家庭时，才能纳入这个家庭视图。例如，孩子尚无客户档案时，可以将其作为简要成员；孩子的保单仍登记在实际管理此事的客户档案下，再把被保险人关联到孩子。若客户属于多个家庭，保单不会自动出现在所有家庭，需在相关家庭中显式纳入。

首版不根据“配偶的父母”等间接关系自动推断新的连线。更换主要服务联系人只改变服务联系人标识，不改写已确认的成员关系。

## 4. 页面与用户流程

### 4.1 入口和建档

1. 客户列表、首页跟进入口及服务事项中的客户链接统一进入 `/clients/:customerId`。客户详情增加“所属家庭”区域：没有家庭时提供“建立家庭 / 加入已有家庭”，已加入时显示家庭名称、成员数和“查看家庭关系”。
2. “建立家庭”预选当前客户为主要服务联系人，填写家庭名称。可以搜索并添加已有客户，或添加仅有称呼的简要成员；添加成员时可选择与家庭内一位已有成员的关系，也可先标记“关系待确认”。
3. “加入已有家庭”由代理人手动选择家庭并确认与现有成员的关系；若同一客户已在该家庭，显示现有成员而不重复创建。搜索客户时只返回选择所需的简要信息。
4. 简要成员以后可关联一个已有客户档案，沿用原家庭成员及其保单关联，不新增第二个成员；关联前展示同名候选，但不自动确认。

### 4.2 客户独立详情页

客户详情完整呈现在工作区，不再使用抽屉承载主内容。顶部为“工作台 / 客户与保单 / 客户列表 / 客户姓名”的面包屑、客户摘要及编辑入口；主体按“概览、保单、家庭关系、服务事项与跟进”组织。保单卡片、核实状态、待办操作、真实沟通记录和现有编辑表单继续复用，编辑操作可保留弹窗。

直接访问或刷新 `/clients/:customerId` 时按 URL 中的 ID 请求客户详情，不依赖此前已加载的客户列表；记录不存在时给出返回客户列表的入口。从家庭图谱进入时可带受限的 `familyId` 上下文参数，面包屑显示家庭路径并提供“返回家庭关系”，不可将任意外部 URL 当成返回地址。浏览器前进/后退需恢复页面与选中的标签。

### 4.3 家庭列表与关系图页面

在“客户与保单”增加“家庭规划”标签页，列表使用 `/clients?view=families`；具体家庭进入 `/families/:familyId`，顶部面包屑为“工作台 / 客户与保单 / 家庭规划 / 家庭名称”。关系图需要完整页面空间：宽屏图谱与成员信息面板并列，窄屏图谱在上、成员信息在下；图谱容器有明确高度、适应窗口的缩放和“重置视图”操作。刷新或直接访问两个地址时均能恢复页面。本次页面仍主要提供关系与保障整理，后续在同一路由增加家庭财务、风险和方案区域。

| 页面区域 | 显示内容与操作 |
| --- | --- |
| 家庭列表 | 按名称/成员搜索；显示主要服务联系人、成员数、已关联保单数、待关联保单数；可新建家庭。 |
| 家庭摘要 | 家庭名称、主要服务联系人、成员数、已关联保单数、待核实数、正在处理的保单服务事项数。保单数按不同保单 ID 计数。 |
| 关系图 | 每位成员一个可选中节点；已确认的成员关系为带文字标签的连线。亲子连线从 A（父母）指向 B（子女），线尾显示箭头，标签根据节点实际位置标示左右或上下方向。主要服务联系人有视觉标识，未确认关系的成员为无连线节点。支持平移、缩放、适应画布、明暗主题；不通过拖拽节点或连线直接修改业务关系。 |
| 节点信息面板 | 点击成员节点后展示称呼、客户/简要成员状态、与其直接相连的已确认关系、相关保单及服务事项。已建档客户提供“查看完整客户档案”链接；简要成员提供“编辑成员/关联客户档案”。 |
| 关系管理 | 通过“添加关系”和点击连线后的表单设置两端成员、关系类型、方向及可选说明；删除连线不删除成员。图谱变化保存成功后更新页面。 |
| 人员保障 | 在关系图下方按成员与医疗、重疾、寿险、意外、其他人身险分类展示保单；卡片显示公司、险种、资料与合同状态、关键日期和服务关系。宽屏可用矩阵，窄屏按成员折叠成卡片。 |
| 财产保障 | 按车辆、房屋/家庭财产等投保对象展示已关联保单；没有对象关联的财险保单进入“待关联”区。此区只说明保单与对象的关系，不展示家庭净资产或财产总值。 |
| 待核对区 | 分开展示“可关联保单”（家庭客户成员名下、尚未纳入家庭）和“归属待确认”（已纳入但未指定保障对象、未分类或资料未核实）；可直接打开归属编辑。 |
| 服务事项 | 汇集本家庭已纳入保单的开放服务事项，点击沿用现有事项详情；不把某位客户所有普通联系待办自动算成家庭待办。 |

图谱负责直观查看关系，同时提供可用键盘操作的成员与关系列表，列表选择与节点选择同步；不能把重要操作只放在连线或悬浮提示里。节点点击只切换面板，不立即跳转页面。图谱上不显示电话、完整保单号或长段敏感资料。打开保单后沿用现有保单和服务操作。所有新增、编辑、关联与解绑按钮显示 loading，防止重复提交，并反馈可读错误。

### 4.4 关联已有保单

从家庭详情点击“关联保单”，候选仅列出该家庭已关联客户名下的保单；先选保单，再确认投保人、被保险人、投保对象与展示分类。可根据保单原有 `holder_name`、`insured_name` 显示提示，但不能直接当作已确认的成员关联。保存前展示“保单管理客户”和“实际保障对象”，以便发现两者不同。

一份保单允许多位被保险人；同一成员可以兼任投保人和被保险人。保单与家庭解绑时只删除该家庭的引用和角色关联，原客户保单、合同状态、服务事项不受影响。若移除的是被保险人或投保对象，相关角色关联同步清理，保单留在该家庭的“归属待确认”区；若移除的是这份保单的管理客户，则该保单必须同时从家庭解绑，否则会违反保单候选范围。

## 5. 关系图库选型与接入边界

| 方案 | 与本需求的匹配点 | 主要实施代价 |
| --- | --- | --- |
| [`@relation-graph/react`](https://www.relation-graph.com/docs/start-react/) | React 专用包直接接收节点与连线数据，提供节点/连线点击、内置中心/树/力导向布局，以及自定义 React 节点插槽；适合以浏览和选择关系为主的家庭视图。 | 需先验证当前项目 React 19、开发态 Strict Mode、明暗主题及自定义节点尺寸下的实际表现；避免每次选中节点都整体重置图谱。 |
| [AntV G6](https://g6.antv.antgroup.com/manual/getting-started/integration/react) | 布局、画布交互和自定义能力更丰富，适合以后演进为较大的关系网络。 | React 页面需管理图实例创建、更新与销毁；业务卡片节点还要接入 React 扩展，首版集成工作更多。 |
| [React Flow](https://reactflow.dev/learn/layouting/layouting) | 自定义 React 节点与节点选择很直接。 | 官方说明自动布局通常要另接 Dagre、ELK 等库；本项目主要展示亲属关系，首版依赖与布局代码会增加。 |

**推荐：** 首版采用 `@relation-graph/react`，关系图组件按需加载；图谱数据由后端家庭成员与关系记录转换而来，业务状态仍在 React feature hook 和服务端维护，不以图库内部状态作为唯一数据源。以主要服务联系人为视觉中心，使用适合非纯树关系的中心布局；配偶、父母子女和兄弟姐妹关系保留真实连线，不为了树形排版添加虚构边。图谱默认是查看与选择模式，新增/编辑关系通过明确的表单提交。

正式安装依赖前先做小范围兼容验证：用项目当前 React 19 渲染 2、5、10、20 个成员的示例图；检验节点点击、关系标签、无连线成员、添加/移除后的稳定布局、开发态重复挂载、窄屏和双主题。通过后锁定实际验证的包版本；若兼容性或布局可读性不达标，再用 G6 做同一数据集对比，不同时引入多个图库。图库渲染问题不能影响文字成员列表和家庭保单查看。

## 6. 汇总口径与展示边界

1. **资料核实与合同状态分开。** 只有“资料已核实且合同状态为保障中”的保单进入“已确认保障中”分组；其他保单显示“待核实”“合同状态待确认”“待生效”“已到期”等实际记录状态。日期已过仍沿用现有规则提示核对，不自动判定合同失效。
2. **没有关联不代表没有保障。** 人员或财产格子中没有保单时显示“未录入相关保单”；旧保单未完成归属时显示待关联提醒，不归到任意成员名下。
3. **不做简单金额求和。** 当前保费、保额和责任摘要是自由文本，不同责任的金额、期间和给付条件也不能直接加成一个“家庭保障总额”。首版按保单展示原始摘要，不提供总保额、保障缺口或自动方案结论。
4. **同一保单去重。** 多位被保险人或多个分类下可重复展示同一保单，但家庭摘要、服务事项和列表统计只按保单/事项 ID 去重。
5. **联系授权独立。** 主要服务联系人、其他客户成员的联系意愿各自生效；家庭关系不授予联系其他成员的权限。简要成员不显示“安排联系”操作。

## 7. 数据结构与迁移方案

使用下一编号的版本迁移，例如 `backend/migrations/005_family_coverage.sql`；不把建表和回填逻辑继续加入每次启动执行的 `schema.sql`。建议的数据结构如下，字段名可在编码时依现有命名约定微调，但关系和约束保持一致：

| 表 | 关键字段与约束 |
| --- | --- |
| `families` | `id`、`name`、`primary_customer_id`、创建/更新时间；主要联系人必须是本家庭已关联客户，由事务校验。 |
| `family_members` | `id`、`family_id`、可空 `customer_id`、仅简要成员使用的 `guest_name`、备注；客户和简要称呼二者恰有其一；同一家庭内 `customer_id` 不重复。 |
| `family_relationships` | `id`、`family_id`、`member_a_id`、`member_b_id`、类型、可选自定义标签、创建/更新时间。亲子关系约定 A 为父母、B 为子女；配偶/伴侣及兄弟姐妹为对称关系。禁止自己连接自己；同一无序成员对首版只保留一条当前关系，反向重复或冲突应拒绝。两端都必须属于同一家庭。 |
| `family_insured_objects` | `id`、`family_id`、类型、显示名称、备注；只存整理保障所需的最少信息，不复用为资产价值台账。 |
| `family_policies` | `family_id` 与 `policy_id` 唯一组合；只能关联该家庭客户成员名下的保单。 |
| `family_policy_people` | 家庭保单、家庭成员、角色（投保人/被保险人）的关联；同一保单可有多个被保险人，同一成员可有不同角色。 |
| `family_policy_objects` | 家庭保单与家庭投保对象的关联；同一对象可有多份保单。 |
| `policy_coverage_tags` | 保单 ID 与人工选择的展示分类，组合唯一；分类属于保单本身，不因家庭不同而复制，在一处修改后所有关联家庭都会看到更新。 |

外键与删除规则：家庭解散时级联删除其成员、关系连线、投保对象和保单关联；**不删除**独立的客户或保单。移出成员时，其关系连线与保单角色同步清理；保单被删除时，家庭保单及其人员/投保对象关联随之清理；客户删除时，其成员关联、名下保单及依赖数据不能留下孤儿。若删除或移出的是主要服务联系人，先要求指定另一位已建档成员，或解散家庭；接口不能留下没有可用主要联系人的家庭。关系两端、成员/投保对象与家庭保单的归属关系须经外键或事务校验，不能跨家庭串联。家庭 ID、客户 ID、保单 ID、无序关系成员对和保单角色组合建立必要的唯一索引；列表按查询条件分页。

### 7.1 后续家庭财务数据的预留边界

后续实施家庭财务现状时，另建**家庭财务资料与快照**，不要把金额、产权和贷款余额直接加到 `family_insured_objects`。至少区分资产、负债、收入、支出、家庭目标和风险事项；每条资料保留归属成员或共同归属、统计日期、币种、金额或范围、资料来源、确认状态及更新时间。可记录“未知/未提供”，不要以零替代。房屋、车辆等真实资产可以通过明确的关联 ID 指向对应投保对象，不能仅凭名称自动配对。同一客户出现在两个家庭时，财务资料不能自动复制或相加；需确认所属家庭和权属，避免重复计算。

保单现有 `premium`、`coverage_summary` 等自由文本继续作为原始资料。后续若要计算保费负担、责任覆盖或方案差异，应增加已核实的结构化责任、金额、币种、期间及适用条件，保留其来源和核对日期；未经核实的文本不能自动参加数值汇总。家庭资产负债、现金流、风险与目标的计算规则应在下一阶段单独评审，并明确资料缺失、估值日期不同和共同产权时的展示方式。

未来计划书引用一版已确认的家庭资料快照、保单资料版本、分析假设及生成时间，代理人可追溯当时为何形成某个方案；方案编辑与客户反馈不回写原始事实。敏感财务资料按最小必要范围采集，并与客户联系授权和页面可见范围分别管理。

### 7.2 投资持仓与估值的扩展预留（后续实施）

**本次需要保证：** `families`、`family_members`、`family_insured_objects` 和保单关联使用稳定主键；家庭详情 API 按成员、保单、投保对象等领域组织数据，不把未来财务字段塞进关系图节点或 `family_insured_objects`。本次迁移只建立当前业务需要的表和约束，不预建空的投资账户、持仓或估值表，也不保存外部平台凭据。后续新增版本迁移和独立领域操作，不需要重建家庭关系与保单归属。

**后续建模方向：** 家庭财务台账先支持人工记录；再按需要新增投资账户/数据源、持仓、估值历史和同步任务等独立表。账户及持仓引用家庭 ID 和已确认的成员归属，可能关联已有资产台账条目；估值记录保留金额、币种、估值时点、获取时点、来源和状态，不能用最新值覆盖历史。外部账户标识只作去重与溯源，密钥/令牌不得明文进入业务表、接口响应或日志。同一成员属于多个家庭时，数据源授权及账户归属需分别确认，避免跨家庭自动复制或合计。

**后续代码接口方向：** 在家庭财务领域操作与外部数据源之间定义可替换的适配层，统一输出账户、持仓、估值和来源信息；人工录入、文件导入与第三方连接使用同一内部数据口径，页面和计划书只消费经校验的家庭财务资料。第三方连接、权限、同步失败、撤销授权与数据重试由该领域单独处理，不写入 `family-coverage-operations.js`。预计通过独立的家庭财务 API 提供查询、确认与快照能力；实际 URL、字段和提供方适配器在实施该阶段时评审，**本次不提供空接口或假数据**。

迁移不自动创建家庭，也不按姓名回填旧保单的投保人/被保险人关联。旧保单仍留在原客户档案；创建家庭后，系统把可选保单列为候选，由代理人逐份核对。迁移需在一次性数据库副本上验证首次执行、重复启动及失败回滚，不能覆盖已有数据。

## 8. 接口与后端规则

| 接口 | 用途与主要校验 |
| --- | --- |
| `GET /api/families`、`POST /api/families` | 分页搜索与建立家庭；创建时校验主要联系人存在，并在事务中加入首位成员。 |
| `GET /api/families/:familyId`、`PATCH /api/families/:familyId`、`DELETE /api/families/:familyId` | 家庭详情、名称/主要联系人调整、解散家庭；详情返回关联数量，界面先展示影响范围再提交删除。 |
| `GET /api/customers/:customerId/families` | 客户详情中的家庭入口；该客户可关联多个家庭。 |
| `GET /api/customers/lookup?search=...` | 添加已有客户时使用的简要候选查询，不加载所有保单和跟进。 |
| `POST /api/families/:familyId/members`、`PATCH /api/families/:familyId/members/:memberId`、`DELETE /api/families/:familyId/members/:memberId` | 加入已有客户/简要成员、编辑成员资料、把简要成员关联为已有客户、移出成员。 |
| `POST /api/families/:familyId/relationships`、`PATCH /api/families/:familyId/relationships/:relationshipId`、`DELETE /api/families/:familyId/relationships/:relationshipId` | 建立、修改或解除两位成员间的确认关系；校验两端、方向及重复成员对，解除关系不删除成员。 |
| `POST /api/families/:familyId/insured-objects`、`PATCH /api/families/:familyId/insured-objects/:objectId`、`DELETE /api/families/:familyId/insured-objects/:objectId` | 管理车辆、房屋/家庭财产等投保对象；不在此接口保存资产估值或负债。 |
| `GET /api/families/:familyId/policy-candidates` | 仅返回家庭客户成员名下、尚未纳入该家庭的保单摘要。 |
| `PUT /api/families/:familyId/policies/:policyId`、`DELETE /api/families/:familyId/policies/:policyId` | 幂等地保存或解除家庭保单关联；一次事务核对客户归属、人员角色、投保对象及分类。 |

核心请求约定：建立家庭传入 `{ name, primaryCustomerId }`；添加成员在 `{ customerId }` 与 `{ guestName }` 中二选一，可同时传入 `relationship: { otherMemberId, kind, label }` 由同一事务创建首条连线，也可暂时不填关系。独立新增连线传入 `{ memberAId, memberBId, kind, label }`；`kind=parent_child` 时 A 为父母、B 为子女。关联保单传入 `people: [{ memberId, role }]`、`insuredObjectIds: []`、`coverageTags: []`。关联保单允许暂时没有人员或投保对象，但必须在“归属待确认”区明显显示。修改主要服务联系人不改动已确认连线。

后端新建 `backend/family-coverage-operations.js` 承担校验、聚合查询和事务；`WorkbenchService` 继续作为控制器兼容门面。控制器、`src/api.js` 与服务方法同步更新。全部 SQL 参数化。建立家庭、关联成员/关系和保单的多表写入使用事务；重复提交由唯一约束和幂等的 `PUT` 行为兜底。家庭详情按成员、关系、保单、事项分批查询，返回稳定的成员与关系 ID，不在客户列表中逐条加载整个家庭，避免查询数随客户数增长。返回节点摘要时保留现有电话和保单号脱敏规则。

家庭财务、投资持仓和估值将来通过独立领域操作、适配器及 API 接入，再由 `WorkbenchService` 组合；当前家庭 API 只返回已实现的关系、保障与服务资料。家庭详情前端按领域组件组织，为后续增加“财务现状、风险、方案”区域留下组合位置，不让图谱组件承担财务数据状态或外部同步逻辑。

## 9. 前端落点与实施顺序

1. **迁移和服务端：** 建表及索引，完成家庭成员、成员关系、投保对象和保单角色的校验与查询；补充旧保单候选查询和删除/解绑事务。复用现有合同状态、服务事项及客户序列化口径。
2. **路由与客户详情：** 扩展 `src/navigation.js` 为可识别 `/clients/:customerId` 和 `/families/:familyId` 的路由解析，仍把两者归入“客户与保单”菜单；保留 `/clients?view=tasks|services|families`。动态详情路径不能被现有固定路径校验重写成 `/` 或 `/clients`。把 `CustomerOverlays.jsx` 的主抽屉内容拆为 `src/features/customers/CustomerDetailPage.jsx` 与表单弹窗组件，详情按 URL ID 加载；客户列表、首页、服务事项与通知的入口改为导航到该路由。
3. **家庭与图谱：** 在 `src/features/customers/` 下新增家庭列表、家庭详情、图谱适配组件、节点信息面板和所属 hook；先完成文字成员/关系列表，再按选型验证结果接入 `@relation-graph/react`。图库只接收整理后的节点/边和选择回调；关系的增删改仍走本项目 API。家庭详情页按业务区域组合，后续可增加财务、风险和方案组件；`App.jsx` 只组合 feature，不加入整页 JSX 或新的领域状态。
4. **保单归属与展示：** 增加候选保单、成员角色、投保对象与分类表单；关系图、人员保障、财产保障和服务事项使用同一家庭详情数据，更新后局部刷新并保持当前选中成员。
5. **呈现与验证：** 面包屑、返回路径、浏览器前进/后退、直接访问和刷新均可恢复。补齐窄屏、明亮/黑暗主题、空状态、图谱加载失败时的文字列表、所有请求按钮 loading 和错误提示。后端集成测试覆盖事务与数据约束，前端纯逻辑测试覆盖汇总去重、关系方向和路由解析；浏览器验证实际点击流程，并在 `docs/` 记录结果。

## 10. 验收场景

1. 分别来自线下拜访和内容渠道的两位客户可加入同一家庭；两人原有来源、阶段、联系授权、跟进和保单归属保持独立。从任一客户档案都能进入同一家庭。
2. 可添加无客户档案的孩子等简要成员；客户和线索统计不增加。之后将该成员关联到已有客户时，原家庭保单角色保留且不产生重复成员。
3. 可在任意两位同家庭成员间手动建立配偶/伴侣、父母子女、兄弟姐妹或自定义关系；亲子方向正确显示。反向重复、自己连接自己、跨家庭连接和同一成员对的冲突关系被拒绝；删除连线不删除两端成员。无连线成员显示“关系待确认”，不画虚构关系。
4. 关系图节点点击后展示该成员资料、直接关系、保单与相关服务事项；打开完整客户档案才进入 `/clients/:customerId`。连线点击可查看/编辑关系；文字成员/关系列表也能完成相同的选择操作。
5. 从客户列表、首页、服务事项及家庭图谱打开的客户详情为独立页面。`/clients/:customerId` 直接访问和刷新可读取同一客户，面包屑能返回列表；从家庭进入时还可返回原家庭。浏览器前进/后退不丢失当前路径，也不弹出旧的客户抽屉。
6. 同一客户可在两个家庭中出现；只有显式纳入该家庭的保单才在该家庭显示。同一家庭不能重复添加相同客户或相同保单。
7. 一份保单可关联不同的投保人和被保险人，也可有多位被保险人；人员卡片都能找到该保单，家庭总数只计一次。财险保单可关联车辆或房屋/家庭财产对象。
8. 旧保单即使 `holder_name`、`insured_name` 与某个成员同名，也只显示为可关联候选；未人工确认前不纳入家庭，不自动判定该成员受保障。
9. 合同状态待确认、资料待核实、记录到期日已过时均按已有保单规则展示；无保单的成员只显示“未录入相关保单”，页面不生成缺口分数或合计保额。
10. 关联其他家庭的成员/投保对象或家庭外客户名下保单时，服务端拒绝请求且不写入部分数据。解绑、成员移出、家庭解散及客户/保单删除后没有悬空关联；独立的客户与保单不会因家庭解散而消失。
11. 家庭服务事项只聚合已纳入保单的开放事项，并按事项 ID 去重。家庭页、客户页、保单服务页可以相互跳转。
12. `/clients?view=families`、`/families/:familyId` 及 `/clients/:customerId` 直接打开和刷新恢复；图谱重置、搜索、建立家庭、关联、编辑、解绑、取消和接口失败状态均可见；窄屏及两种主题可正常使用。图谱无法加载时文字列表仍可查看资料。
13. 家庭页面清楚标示本阶段只整理关系、已有保障和投保对象；投保对象没有资产估值字段，页面不生成净资产、现金流或风险评分。后续家庭财务资料可使用稳定的家庭、成员、保单和投保对象 ID 建立明确关联，而无需从姓名或对象名称猜测归属。
14. 本次家庭详情 API 与图谱组件不包含投资账户、持仓和估值字段；后续可通过新迁移和独立财务领域接口关联已有家庭/成员 ID，保留既有客户、保单和家庭数据。未接入外部数据源时页面不显示伪造的实时估值。

实施时运行 `npm run build`、`npm run test:ui-logic`，并仅在**一次性、可丢弃的 PostgreSQL 测试库**上运行 `npm run test:api`。家庭视图不需要调用真实 Runware、Humanizer 或 Baoyu，也不触发社交平台发布。

## 11. 实施采用的默认选择

1. **页面位置：** 家庭列表作为“客户与保单”的“家庭规划”标签页，不增加一级菜单；家庭详情和客户详情分别使用独立路由与面包屑。
2. **多家庭归属：** 允许同一客户出现在多个家庭，但保单必须在每个家庭显式纳入；避免自动扩散资料。
3. **关系口径：** 首版记录任意两位家庭成员间经过人工确认的直接关系；主要服务联系人只是业务标识，不作为所有关系的唯一参照。不推断间接关系。
4. **图库：** 首版接入 `@relation-graph/react`；React 19、Strict Mode、窄屏与双主题的真实浏览器兼容验证仍在待完成验收项中。
