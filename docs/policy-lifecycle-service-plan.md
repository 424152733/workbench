# 保单全周期与服务事项实施计划

**版本：** 1.0（已实施）  
**日期：** 2026-10-16  
**状态：** 首版已实施；验证结果见 [测试报告](./policy-lifecycle-service-test-report.md)  
**范围：** 客户与保单、工作首页、工作台内提醒  
**目标用户：** 当前工作台的单人保险代理人

## 1. 目标与业务边界

围绕客户的一份具体保单，记录可核实的合同状态、关键日期，以及缴费、续保、保全、理赔咨询等服务事项。代理人能看到下一步该做什么、事项为何等待、何时完成，以及处理过程中发生了哪些联系和状态变化。

保单与服务事项分别管理状态：一份保单可关联多项服务事项，一项服务事项也可关联多次客户联系。完成一次联系不会自动结案；完成服务事项也不会自动改变合同状态。客户来源和内容渠道关联继续保持独立，线下客户与外部保单使用相同的记录流程。

本轮只在工作台内记录、提醒和展示。缴费由客户通过保险公司认可的渠道办理；保全和理赔结果以保险公司正式记录为准。工作台不代替保险公司确认合同效力，不自动登录外部系统，也不发送短信、微信或桌面通知。

## 2. 当前基线

| 已有能力 | 当前数据与交互 | 本轮需要补充 |
| --- | --- | --- |
| 保单档案 | `policies` 保存公司、险种、保单号、投保人/被保险人、保费、保障摘要、到期日、服务关系；`verified` 只有“已核实/待核实” | 独立的合同状态、起保日、下次缴费日及可追溯的变更记录 |
| 保单提醒 | 首页统计 30 天内到期的保单；客户详情显示保单卡片 | 从提醒进入对应保单和服务事项，避免只看见数字却无处理路径 |
| 客户联系 | `customer_follow_up_tasks` 管计划中的联系，`follow_ups` 管实际沟通；支持完成、改期、取消和事件历史 | 可选择关联服务事项；联系完成后回到该事项继续处理 |
| 客户页面 | 客户列表与 `?view=tasks` 跟进待办；客户详情为抽屉 | 增加服务事项视图、保单卡片入口及事项详情 |

## 3. 状态与日期语义

### 3.1 保单层

保留现有的**资料核实状态**，另增**合同状态**。二者不互相推断。

| 维度 | 值或规则 | 更新依据 |
| --- | --- | --- |
| 资料核实 | `verified` 现有布尔值 | 代理人核对已有资料后操作 |
| 合同状态 | `unknown` 待确认、`pending_effective` 待生效、`active` 保障中、`suspended` 效力中止、`expired` 已到期、`terminated` 已终止 | 代理人依据合同或保险公司正式信息手动确认；保存确认日期与依据摘要 |
| 日期标签 | 距已录入到期日/缴费日的天数、今天、逾期 | 系统实时计算，仅用于提醒；不写成合同状态 |

新录入及既有保单的合同状态默认 `unknown`。经过到期日时，系统显示“记录的到期日已过，待核对”，不自动改成 `expired`。资料核实标记、合同状态和日期标签在界面分别显示。对外部保单同样记录信息依据，并标识“客户自有 / 外部保单”。

### 3.2 服务事项层

首版类型为 `payment` 缴费、`renewal` 续保、`endorsement` 保全、`claim_inquiry` 理赔咨询、`other` 其他。每项必须关联一位客户名下的**一份具体保单**；尚不能确定对应保单的一般咨询，先使用现有客户跟进待办。

状态为 `pending` 待处理、`in_progress` 处理中、`waiting_customer` 待客户反馈、`waiting_insurer` 待保险公司反馈、`completed` 已完成、`cancelled` 已取消。可以在前四种开放状态之间转换；结案和取消需要结果或原因。首版结案后不直接改写历史状态，如需后续处理则新建关联事项。逾期是根据“下一步处理日”和开放状态计算的标签，不是持久化状态。

| 类型 | 典型处理内容 | 结案记录示例 |
| --- | --- | --- |
| 缴费 | 提醒客户、确认办理渠道、记录核实结果 | 已核对缴费结果 / 客户决定暂不办理；不记录支付凭据或代收款 |
| 续保 | 核对到期信息、了解续保意向、跟踪正式续保结果 | 已续保并核实新合同信息 / 未续保及原因 |
| 保全 | 记录变更诉求、材料与提交情况、跟踪正式处理结果 | 保险公司已确认变更 / 未完成及原因 |
| 理赔咨询 | 记录咨询问题、报案或材料进度、正式答复 | 已提供咨询或已收到正式答复；不自行判定能否赔付 |

## 4. 用户流程与页面交互

```text
首页到期提醒 / 客户详情的保单卡片
           │ 点击“发起服务事项”
           ▼
新建事项：类型、标题、具体保单、下一步处理日、说明
           │ 保存；检查同一保单同一周期的进行中事项
           ▼
事项详情：状态、下一步、进展时间线、关联的客户联系
           ├─ 记录进展 / 改状态 / 改下一步处理日
           ├─ 安排联系 → 现有跟进待办 → 记录真实沟通 → 返回事项
           └─ 完成或取消 → 填结果/原因 → 留在历史列表
```

1. **进入：** `客户与保单` 增加“服务事项”视图，地址使用 `/clients?view=services`；可筛选未完成、已逾期、已完成、类型及客户。客户详情每张保单卡片增加“发起服务”和“查看服务记录”。首页到期提醒可直达对应客户/保单；刷新地址后仍回到服务视图。
2. **新建：** 从保单卡片进入时预选客户与保单；填写类型、标题、下一步处理日和可选说明。服务关系为“客户自有 / 外部保单”时保留明显标识。若同一保单、同一类型、同一日期锚点已有开放事项，先展示已有事项，避免重复创建。
3. **处理：** 事项详情显示当前状态、下一步日期、操作历史与关联的联系待办。记录进展可填写简短摘要；改成“等待反馈”时仍需设置回看日期，避免长期无人处理。安排联系沿用现有跟进待办，遵守客户联系意愿状态。完成联系只写真实沟通和待办完成事件，服务事项继续存在。
4. **结案：** 必填实际处理结果和结案日期。若续保产生新合同，手动新增保单并关联原保单；若原合同继续，核实后再更新原保单的日期/状态。任何合同字段变化都留下变更事件，不由“事项已完成”自动触发。
5. **提醒：** 首页和顶部通知只将今天、逾期的开放事项计入紧急数，未来日期在服务列表可见。若事项的下一步动作已对应一项未完成的客户跟进待办，通知聚合为一条，避免同一动作提醒两次。页面关闭后不另行推送。

## 5. 数据设计与迁移

### 5.1 保单扩展

- `policies` 增加 `effective_date DATE`、`next_payment_date DATE`、`contract_status TEXT DEFAULT 'unknown'`、`status_confirmed_on DATE`、`status_basis TEXT` 和可选的 `renewed_from_policy_id`。保留现有 `verified`、`expiry_date` 与 `service_scope`。
- 新增 `policy_lifecycle_events`，记录保单状态/关键日期变更的前后值、发生日期、依据摘要和记录时间。续保生成新保单时，通过 `renewed_from_policy_id` 串联前后合同；不覆盖原保单号。
- 当前已有的 `verified=true` 不回填成 `active`；旧日期原样保留。只有确认过的信息才写入新合同状态。

### 5.2 服务事项与关联

- 新增 `policy_service_items`：`id`、`policy_id`、类型、标题、说明、状态、`anchor_date`（可选的到期/缴费日期锚点）、`next_action_date DATE`、结案结果、结案时间、创建/更新时间、唯一的创建 `request_key`。客户从保单关联得出，不重复保存 `customer_id`。
- 新增 `policy_service_item_events`：事项外键、动作、变更前后状态/日期、说明、操作时间及请求标识。记录创建、进展、改期、状态变化、结案和取消；历史按时间排序，不用覆盖旧摘要。
- `customer_follow_up_tasks` 和 `follow_ups` 增加可空的 `service_item_id`。服务事项安排的待办和实际沟通可被事项详情追溯；普通客户跟进不需要关联保单。删除客户时，保单、事项、事件及关联的专属待办/沟通随外键级联清理，不留孤儿数据。首版界面不提供事项硬删除，使用取消并留痕；今后若增加保单删除，需用事务及明确的级联规则清理其专属记录。
- 给事项的 `(status,next_action_date)`、`(policy_id,status,created_at)` 建索引。创建请求标识和事件请求标识用于网络重试幂等。开放事项的同保单、同类型、同 `anchor_date` 重复创建由服务端拦截，并返回已有事项。

### 5.3 迁移策略

`DatabaseService` 目前每次启动都会执行含示例数据的 `backend/schema.sql`。本功能新增**有版本号的迁移目录和迁移记录表**：启动时先执行现有可重复初始化脚本，再按版本顺序在事务内执行尚未应用的迁移；并发启动需串行化迁移。新表和新字段只在迁移中定义，不在启动脚本中重复回填业务数据。

迁移只增加字段和表，不根据旧到期日批量生成服务事项，也不改写已有客户、保单和沟通记录。部署前在可丢弃的数据库副本上验证首次迁移、重复启动和回滚恢复；`npm run test:api` 只连接一次性测试库。

## 6. 接口与服务端规则

| 接口 | 用途 |
| --- | --- |
| `PATCH /api/policies/:id/lifecycle` | 修改合同状态或关键日期；校验依据并写保单变更事件 |
| `GET /api/service-items` | 按状态、类型、日期、客户/保单分页查询；逾期优先 |
| `POST /api/policies/:id/service-items` | 新建事项，校验保单存在、类型/日期、重复周期和请求标识 |
| `GET /api/service-items/:id` | 事项详情、事件、关联的待办与沟通 |
| `PATCH /api/service-items/:id` | 改标题、说明或下一步处理日；改期写事件 |
| `POST /api/service-items/:id/progress` | 记录进展并可转换开放状态；写事件 |
| `POST /api/service-items/:id/complete` | 必填结果，事务内结案并写事件 |
| `POST /api/service-items/:id/cancel` | 必填原因，事务内取消并写事件 |
| 现有跟进待办/沟通接口 | 接受可选 `serviceItemId`，核对客户与保单归属一致 |
| 现有看板/通知接口 | 增加服务事项紧急数和入口，聚合重复的联系提醒 |

业务校验放服务层，控制器只接收参数。所有多表变更使用 `DatabaseService.transaction()`；状态转换先锁定事项行，重复提交按请求标识返回既有结果或明确冲突，不重复写事件。查询保持分页，避免客户列表对每份保单逐条读取事项。所有 SQL 参数化。

日期统一使用 `YYYY-MM-DD` 和 `Asia/Shanghai` 业务语义；“今天/逾期”按该时区的日期计算，不依赖 PostgreSQL 服务器时区。没有下一步日期的开放事项不可保存。已拒绝联系的客户仍可记录非联系性质的服务进展，但不能新增联系待办或把服务记录伪装成已发生的沟通。

## 7. 代码落点与实施顺序

1. **数据与迁移：** 新增 `backend/migrations/`、迁移执行器、保单及事项表；核对重复启动、旧数据保留和级联删除。
2. **后端：** 在 `backend/` 新建职责清晰的保单服务操作模块，由 `workbench.service.js` 组合；扩展 `api.controller.js`、客户序列化、看板和通知；复用现有日期与校验纯函数。
3. **前端：** 在 `src/features/customers/` 增加服务事项列表、详情、操作弹层和所属状态 hook；扩展保单卡片和 `src/api.js`。首页入口放 `src/features/dashboard/`，路由视图继续与 `navigation.js` 及地址栏同步。`App.jsx` 只保留跨域组合，不堆入整页业务 JSX。
4. **交互收尾：** 所有接口按钮显示 loading、阻止重复提交并给出可读错误；补齐空状态、明亮/黑暗主题、窄屏布局和键盘可操作性。相应更新 `workbench/docs/` 的实施/验证记录。

## 8. 验收与验证

1. 新旧保单分别显示资料核实状态与合同状态；旧保单默认为“合同状态待确认”。到期日已过只产生核对提醒，不自动改变合同状态。
2. 从新华或人保财险的本人代理保单，以及客户自有外部保单，均能创建并查看服务事项；不允许把事项或联系记录关联到其他客户的保单。
3. 同一保单可有不同类型事项；同一类型同一日期锚点的开放事项不会因重复点击或网络重试产生两份。状态、改期和进展历史完整可查。
4. 服务事项关联的客户联系完成后生成真实沟通记录，事项仍按其自身状态处理；客户拒绝联系时不能从事项新建联系待办。
5. 完成/取消事项需要结果或原因；并发或重复结案不产生重复事件。未核实的续保结果不会自动更新保单日期或合同状态。
6. 今日、逾期和未来事项按北京时间正确归类；首页、客户详情、服务视图和通知数据一致，关联联系待办不重复提示。
7. 删除客户时相关保单、服务事项、事件和专属待办/沟通没有孤儿记录。数据库首次迁移与重复启动不会覆盖原数据或再次生成事项。
8. 浏览器走通新建、进展、等待、安排联系、完成、取消、刷新直达 `/clients?view=services`、接口错误、窄屏及两种主题。

验证命令按影响范围运行 `npm run build`、`npm run test:ui-logic`、`npm run test:api`。API 测试必须使用一次性 PostgreSQL 测试库；本功能的验证不调用真实 Runware 文本/图片模型。最后提交实施与测试报告，明确未覆盖的场景。

## 9. 本轮采用的默认选择

1. 所有服务事项都关联具体保单；未确定保单的一般咨询先记在客户跟进中。
2. 合同状态必须由代理人按已核对资料手动确认；日期只触发提醒，不自动判定合同效力。
3. 到期提醒提供“发起续保事项”入口，不自动批量建单。下次缴费日由代理人录入，不从缴费频率推算。
4. 服务事项结案后保留历史；首版不提供硬删除或复开。后续同类需求建立新事项，并可在说明中引用前一事项。
5. 第一阶段优先打通续保和保全的完整交互；缴费、理赔咨询和其他类型沿用同一数据结构与通用表单，在第二阶段补足类型专属字段与验收场景。
