# 多平台保险科普生文提示词优化实施记录

**状态：** 代码实施完成，待真实模型样稿复核  
**版本：** 0.2  
**范围：** DeepSeek 生文、humanizer-zh 润色、小红书图卡规划与生成入参

## 1. 背景与目标

“大话保险”面向普通消费者，用通俗表达解释保险概念、常见误区和需要核实的条款边界。知乎、公众号和小红书的阅读方式不同，生成内容需要分别满足平台的阅读目的：

- 知乎和公众号承担较完整的保险知识讲解。
- 小红书围绕一个问题快速传达重点，适合移动端浏览。
- 小红书图卡与发布配文各自补充信息，不重复粘贴整段内容。
- 三个平台共享已核实的事实和保险边界，但不共享同一篇正文再做格式转换。

本方案优化生文链路，让 DeepSeek 按平台分别构思；让 humanizer-zh 在保持事实和平台结构的前提下润色；让 Baoyu 依据专门的图卡内容规划生成图片，降低图文重复。

## 2. 实施前代码行为

目前 `backend/workbench.service.js` 的 `generateDrafts()` 使用一套通用系统提示词，要求模型返回知乎、小红书、公众号三条稿件。提示词强调通俗表达、保险边界和不编造信息，但没有分别定义各平台的内容目标、信息密度和正文组织方式。用户提示词只额外要求公众号摘要、小红书标签。

选题可以配置发布平台，但生成请求仍要求模型返回三平台稿件，之后才筛选选题实际启用的平台。

`backend/skill-runner.js` 中的 humanizer-zh 说明主要是自然化文字、保留事实、移除 Markdown 粗体。批量输入中有平台名称，但编辑要求没有区分知乎回答、公众号文章和小红书短文的结构。

小红书图像生成时，服务端将整篇小红书正文作为 Baoyu 的 `text` 输入，并要求技能从正文规划 3–5 张卡片（测试模式 1 张）。目前草稿数据结构没有单独保存卡片文案或图卡大纲，因此配文和图卡内容可能来自同一段素材。

公众号正文已有富文本 HTML 导出；本方案保留现有预览、导出、审批、复制发布和图片生成功能。

## 3. 目标与非目标

### 目标

1. 按平台阅读场景分别生成内容，不把一份通用短文机械拉长或换格式。
2. 增加知乎和公众号的必要解释深度，同时避免为了篇幅凑字数。
3. 让小红书卡片文案与配文承担不同职责，并将专门的图卡规划传给 Baoyu。
4. 润色后保持平台结构、关键事实、确定程度、条款边界和来源信息。
5. 生成结果可校验、可保存、可追溯，并在 UI 中继续编辑和人工审核。

### 非目标

- 不改变 DeepSeek 文本模型、Runware 图片模型及其 API Key 配置。
- 不改变 Baoyu 技能的来源和小红书测试/生产张数规则。
- 不增加自动发布能力；现有“复制后自行发布”流程保持不变。
- 第一阶段不新增提示词编辑页面，也不要求用户维护字数配置。
- 不让模型补造保险产品条款、当地政策、理赔结果、统计数字或真实客户故事。

## 4. 平台内容契约

以下是生成质量要求，不是不可变的字数上限。具体篇幅由主题复杂度决定，提示词要求“讲完整，不凑字数”。

### 4.1 知乎：围绕问题作答

- 标题或开头对应一个具体疑问；首段先给简明结论。
- 解释相关概念和判断依据，明确容易混淆的概念。
- 结合主题说明常见误区、需要核对的条款或情形；不为了丰富而虚构案例。
- 复杂内容可以使用自然小标题和清单，结尾收束要点并说明适用边界。
- 使用知乎回答语气，不写成公众号导语，也不塞入小红书标签。

### 4.2 公众号：完成一篇系统科普

- 输出适合单独阅读和分享的标题、摘要、完整正文。
- 正文根据主题需要安排背景或读者疑问、概念解释、分节讲解、实用核对清单、总结与边界说明。
- 各段之间有自然衔接；可以详细解释术语、责任范围和阅读条款的方法。
- 仅在确有帮助时使用示例，并明确标识为假设说明；不编造真实人物、金额、产品规则或理赔结论。
- 不通过重复同一结论、冗长开场或重复免责声明扩充篇幅。

### 4.3 小红书：一个主题，快速读懂

- 一条稿件聚焦一个疑问或一个可执行的判断方法。
- 正文/配文保持精炼，承担开场、图片之外的解释、必要提醒和自然互动引导。
- 图片卡片逐张传递不同的信息点，例如封面问题、核心概念、核对要点、常见误区、结尾提醒；具体卡片数仍由现有测试/生产模式控制。
- 卡片不重复发布配文的完整句段。封面标题或一句核心结论可以有意重复，帮助读者快速理解。
- 保险责任、免责、地区差异等关键边界不能因精简而删除；可以放在适合阅读的位置，不必在每张图重复。
- 沿用现有标题长度和话题标签约束。

## 5. 建议的生成数据结构

继续使用现有 JSON 响应，不改变知乎、公众号、小红书的 `title`、`summary`、`body`、`hashtags`、`sources` 字段含义；只为小红书增加一份独立图卡规划：

```json
{
  "drafts": [
    {
      "platform": "知乎",
      "title": "问题式标题",
      "summary": "",
      "body": "知乎回答正文",
      "hashtags": "",
      "sources": ""
    },
    {
      "platform": "公众号",
      "title": "文章标题",
      "summary": "文章摘要",
      "body": "公众号完整正文",
      "hashtags": "",
      "sources": ""
    },
    {
      "platform": "小红书",
      "title": "短标题",
      "summary": "",
      "body": "精炼发布配文",
      "hashtags": "话题标签",
      "sources": "",
      "cardPlan": [
        {
          "role": "cover",
          "headline": "卡片标题",
          "keyPoints": ["一个重点", "必要补充"],
          "visualDirection": "画面构图说明"
        }
      ]
    }
  ]
}
```

模型只需要为选题启用的平台返回稿件；缺少必需字段、返回重复平台或返回未启用平台时，服务端应清晰报错，避免静默套用其他平台内容。`cardPlan` 保存完整的生产规划（3–5 张），每张卡片有独立角色和要点，视觉说明不引入新保险事实。测试模式只把封面卡片交给 Baoyu 生成 1 张测试图；生产模式才发送完整规划。这样测试不会丢失后续生产要用的图卡结构。

### 卡片规划持久化建议

当前 `drafts` 表没有卡片规划字段。建议新增 `xhs_card_plan JSONB NOT NULL DEFAULT '[]'`，并同步加入 draft 查询、保存、生成响应和 `draft_versions.snapshot`。数据库 schema 每次启动会重复应用，因此除 `CREATE TABLE` 定义外，也需要执行 `ALTER TABLE drafts ADD COLUMN IF NOT EXISTS ...`，确保已有数据库升级且初始化可重复。这能保证刷新、编辑、重新生成和历史版本中的卡片规划一致，也使 Baoyu 可直接使用已审核的规划。

如果评审希望先避免数据库迁移，可考虑将规划仅放在现有图片生成请求中临时生成；但这会增加一次模型规划步骤，且重新生成图片时卡片结构可能变化。建议采用数据库 JSONB 字段方案。

## 6. 提示词与处理链路改造

### 6.1 DeepSeek 生文

- 将通用系统提示词拆成“栏目统一规则 + 平台内容契约”。
- 栏目统一规则负责大白话、事实准确、保险边界、来源和合规表达。
- 每个平台使用独立写作说明，直接引用第 4 节的目标和结构要求。
- 动态传入选题、类别、用户设置的表达偏好、可用平台，以及已提供的资料来源。
- 只生成启用平台的内容；同一主题中的稿件共享事实，但各自重新组织论述。
- 明确篇幅由主题复杂度决定，不凑字数、不重复段落、不为扩写补造事实。
- 生成小红书稿件时同时返回配文和完整的 3–5 张生产卡片规划，卡片规划要点之间不重复；图片测试模式只取封面卡片，不缩减已保存的完整规划。

### 6.2 humanizer-zh 润色

- 继续由 humanizer-zh 执行中文自然化，不让它承担事实查证或补充新知识。
- 将平台名称与平台契约一并交给润色阶段：保留知乎回答结构、公众号文章层次、小红书的精炼配文。
- 不把长文压成短文，也不把短文扩写成文章；不改变小红书图片与配文的分工。
- 对小红书卡片规划的文字做同样的自然化润色，但只修改表达，不改变每张卡片的要点、顺序和角色。
- 保留所有数字、否定、来源、产品/地区限定和保险责任边界；继续遵守现有“不要出现 `**` Markdown 粗体标记”等表达规则。

### 6.3 Baoyu 小红书图卡

- 生图输入从“小红书整篇配文”改成“标题 + 已保存的 cardPlan + 图卡样式配置”；测试模式只选择封面卡片，生产模式使用全部已规划卡片。
- 指示 Baoyu 按卡片角色和要点设计图像，不重新提炼或复制整段配文。
- 卡片上的中文文字以 cardPlan 中已审阅的 headline/keyPoints 为准，不新增、删改保险事实。
- 继续遵守测试模式 1 张、生产模式 3–5 张、现有图片样式配置和人工检查流程。
- 图片文字清晰度仍由生图模型和人工复核共同保障；审批前检查文字、事实、素材和署名。

### 6.4 公众号及知乎图像输入

公众号和知乎继续沿用现有 Baoyu 文章插画流程，不纳入小红书“图卡与配文分工”的数据库字段和卡片张数规则。提示词可以明确插图用于解释正文概念，不重复生成整段文章文字。

## 8. 验收标准

1. 只生成选题上启用的平台，返回的稿件平台集合与选题一致。
2. 用同一选题生成三个平台稿件时，三者有清晰的阅读目标和结构差异；共享事实但不复制成三份同文。
3. 知乎稿件先回答问题并提供解释依据；公众号稿件能作为独立文章完整阅读；均不靠重复和虚构内容拉长。
4. 小红书配文简洁，图卡规划中的卡片承担不同信息角色；除封面/核心结论等有意重复外，不复述整段配文。切换测试/生产生图模式时，完整生产规划保留，测试只提交封面卡片。
5. Baoyu 收到小红书图卡规划和当前样式配置；不会收到整篇配文作为唯一图像内容来源。
6. humanizer-zh 不改变平台结构、卡片角色、事实程度、来源和保险边界；不产生“第一步/第几步”模板化表述或 `**` 标记。
7. 生成、编辑、刷新、重新生成、版本查看和 Baoyu 生图均能正确保存/读取卡片规划。
8. JSON 格式异常、缺少平台稿件或卡片数量不符合模式时，在生图扣费前返回可理解的错误；不提交任何 Runware 图片任务。
9. 新旧数据库初始化可重复执行，已有稿件和图片不丢失；不触发自动发布。
10. 自动化测试覆盖平台 prompt 构造、输出字段校验、卡片规划持久化、版本快照、humanizer 输入及生图请求内容；浏览器逐平台走通生成与审核编辑流程。

## 9. 实施顺序

1. **提示词与数据契约：** 敲定平台契约、JSON 结构和旧稿兼容方式。
2. **服务端与数据库：** 实现动态平台生成、卡片规划存储/校验、humanizer 和 Baoyu 入参。
3. **前端编辑与预览：** 增加小红书图卡规划查看/编辑，并接通保存和重新生图。
4. **自动化验证：** 使用 mock DeepSeek、mock humanizer 和 mock Runware 验证调用内容与费用边界。
5. **浏览器验证：** 分别检查知乎长文、公众号长文、小红书配文/图卡规划及审核状态。
6. **真实模型小样：** 先生成稿件文本并人工审阅，再由用户决定是否调用付费生图。

## 10. 已确认的实施决策

1. 小红书卡片规划独立存储为 `xhs_card_plan JSONB`，刷新和版本快照均保留完整规划。
2. 生成时只传入选题启用的平台，模型输出平台集合必须与选择一致。
3. 暂不设固定字数范围，按主题完整度控制篇幅，观察真实样稿后再评估。
4. humanizer-zh 润色小红书 cardPlan 的文字，并由服务端校验卡片数、顺序、角色及每卡要点数。

## 11. 风险与处理

- **保险事实风险：** 模型可能把一般说明写成具体产品承诺。通过只用已提供资料、强制表达适用边界、来源留空时不臆造和人工审核来控制。
- **格式风险：** 模型可能漏平台、漏卡片或返回非 JSON。由服务端校验完整性；不完整时提示重新生成，不继续调用付费生图。
- **图文重复：** 生图模型仍可能把要点扩写或复述。输入分离为 cardPlan，并在人审清单中增加“图片与配文无整段重复”。
- **中文字形质量：** 图片模型可能出现错字或模糊文字。保留现有人工检查要求；高字量信息优先放在配文，不把长段中文塞进图卡。
- **旧稿兼容：** 旧小红书稿件没有 cardPlan。保留旧稿读取和编辑；重新生图前要求生成/补齐规划，避免静默把旧正文当成卡片脚本。
- **提示词篇幅与生成稳定性：** 三套平台规则和统一安全规则较长。应抽成服务端可测试的 prompt builder，避免散落字符串互相冲突。

## 13. 模型路由更新（2026-10-21）

- 内容工作台的文本调用统一使用 DeepSeek V4.1 Flash（API 模型 ID：`deepseek-flash`）：选题推荐、知乎/小红书/公众号稿件、humanizer-zh 润色、小红书图卡规划及 Baoyu 插画提示词规划。
- Runware GPT Image 只用于最终图片生成。图像任务会先确认 `DEEPSEEK_API_KEY` 和 `RUNWARE_API_KEY` 均已配置，再调用 DeepSeek 做视觉规划，避免图片服务缺失时产生无用的文本模型费用。
- DeepSeek 使用 `DEEPSEEK_BASE_URL`、`DEEPSEEK_TEXT_MODEL` 和 `DEEPSEEK_API_KEY`；图片生成使用 `RUNWARE_IMAGE_MODEL` 和 `RUNWARE_API_KEY`。原有稿件和提示词结构不变。
- 自动化测试全部通过模拟响应验证，没有调用真实 DeepSeek 或 Runware 服务。

### 图卡文案密度调整（2026-10-18）

- 根据使用反馈，小红书图卡不能只由短标题和关键词组成。生成提示词现在建议封面使用 1–2 条短句，解释类卡片使用 2–3 条约 20–35 字的完整短句，每张要点约 50–90 字；简单主题允许更短，禁止重复凑字数。
- Baoyu 输入规则要求按已审核的标题和要点保留必要解释，不能把 keyPoints 再压缩成关键词；视觉布局仍需避免大段文字，并保证手机阅读清晰。
- 编辑区提示和演示用卡片同步调整。保留原有数据结构与长度上限，旧卡片无需迁移；提示词测试检查目标密度，演示卡片测试检查实际文案量。
