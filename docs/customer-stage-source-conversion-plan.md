# 客户阶段与来源转化：实施方案

**版本：** 1.0（已实施，待数据库与浏览器验证）  
**日期：** 2026-10-18  
**范围：** 客户与保单模块的客户分析首期  
**后续顺序：** 完成本期后，再规划家庭结构与保障分布

## 1. 目标与已定口径

顾问需要看清当前客户处于什么阶段、各获客来源带来的线索在 90 天内如何变化，并能区分“建立客户关系”和“实际成交”。统计对象是独立客户档案；一个人即使加入多个家庭，也只按客户 ID 计一次。没有独立客户档案的简要家庭成员不参加统计。

本期交付两个视图：**当前阶段分布**和**来源转化**。页面位于“客户与保单”的“客户分析”标签，地址为 `/clients?view=analysis`。首页现有的“客户来源”圆环继续表示所选月份新增线索的来源构成；分析页展示按获客日期选出的线索群及其转化，不让两个图表共用含义不同的百分比。

| 指标 | 定义 |
| --- | --- |
| 当前阶段人数 | 筛选范围内，每位客户按 `customers.stage` 计入一个阶段；六个阶段均展示，人数之和等于客户档案数。 |
| 新增线索 | **创建时**身份为“新线索”的客户档案；按客户创建时间归入日期范围。直接按“已有客户”建档者不进入线索分母。 |
| 线索转客户 | 上述线索在创建后的 90 天内，首次进入“已成交”或“已有客户”；两种状态合计只计一次。 |
| 成交 | 上述线索在创建后的 90 天内曾进入“已成交”；进入“已有客户”本身不算成交。成交人数是转客户人数的子集。 |
| 来源归因 | 使用建档时保存的获客来源；普通客户资料编辑不会改动归因。明确的“更正获客信息”操作可以修改归因并留下记录。 |
| 转客户率、成交率 | 对每个来源，分别为 `转客户人数 ÷ 可完整观察线索数`、`成交人数 ÷ 可完整观察线索数`。分母为 0 时返回 `null`，界面显示“—”，不显示 0%。 |

“已联系”“需求了解中”列表示在观察期内**确实进入过该阶段**的不同客户数。现有阶段选择器允许跳级，因此这些列不推断被跳过的阶段，也不要求人数逐列递减；界面采用来源对照表，不画带有必经步骤含义的漏斗。同一客户重复进入同一阶段只计一次。达到转客户或成交阶段后，即使后来转入“暂缓跟进”，历史转化仍保留；当前阶段分布会反映最新状态。

## 2. 现有基础与数据缺口

| 现有实现 | 对本期的作用 |
| --- | --- |
| `customers` 保存 `kind`、`stage`、`source_code`、`created_at`；`source_dictionary` 保存代码与中文名称 | 可直接做当前阶段分布和来源名称映射。`kind` 与 `source_code` 都允许后续修改，不能直接充当不可变的获客快照。 |
| `customer_stage_history` 保存 `from_stage`、`to_stage`、`changed_at`；新增和阶段变化会写入历史 | 可计算真实发生的阶段里程碑。早期示例或旧档案可能没有初始阶段事件，不能据当前阶段补造过去的转化事件。 |
| 首页已有按月新增线索来源圆环；客户页已有关注问题汇总 | 可保留现有摘要，新增分析标签专注阶段与转化。 |
| 客户模块用 `?view=tasks/services/families` 保存标签 | 新增 `analysis` 值即可保持地址栏、刷新和浏览器前进/后退一致。 |

本期不把“已有客户”建档数并入新线索转化率，也不根据保单是否存在推断成交。客户来源和阶段均来自人工记录；分析结果不能表示真实销售收入或保险保障是否充分。

## 3. 日期、样本与旧数据

1. 顶部日期筛选按**客户创建日期**，用 `Asia/Shanghai` 将 `customers.created_at` 转为业务日期；`from`、`to` 为包含首尾的 `YYYY-MM-DD`。默认从当前月往前数 11 个月的月初至今天；`to` 不得晚于今天，最大查询跨度 24 个月。来源筛选按**获客来源**，不是客户档案里可编辑的当前来源。
2. 当前阶段分布覆盖日期与来源筛选命中的所有客户，包含直接建档的已有客户、仍在观察期的线索和旧档案；标题明确写“当前阶段”。
3. 转化率只使用创建已满 90 天的线索：`created_at + INTERVAL '90 days' <= 统计时点`。阶段事件必须发生在 `[created_at, created_at + INTERVAL '90 days')` 内，且不晚于统计时点。未满 90 天的线索计入“观察中”，可显示当前阶段，但不进入转化率分母。
4. 正式转化率还要求获客来源与初始身份的 `basis` 为 `captured` 或 `manually_confirmed`，并存在 `from_stage IS NULL AND to_stage='新线索'` 的初始历史事件。缺少初始事件或只有旧数据快照的线索单列为“历史资料待核对”，不进入正式分母。即使其当前阶段为“已成交”，也不反推发生时间。
5. 旧客户迁移时，用当时的 `kind`、`source_code` 建立一条**旧档案快照**，只供阶段分布和资料核对使用；不伪装成建档当时的来源，也不生成阶段历史。顾问日后明确更正获客资料时可把归因标记为“人工确认”，但缺少初始阶段历史者仍不进入正式的 90 天转化率。
6. 每条新线索按顺序归入且只归入一类：先检查获客快照与初始阶段事件是否可靠，不可靠者归“历史资料待核对”；其余未满 90 天者归“观察中”；剩余归“可完整观察”。页面同时展示三类人数。没有合格样本时给出原因和补录建议；不得把“暂无可计算样本”显示为“0% 转化”。

日期区间是获客群的范围，不是阶段变化发生日期的范围。例如选择 2026 年 1 月的线索，统计它们各自建档后 90 天内的变化。所有查询使用一次固定的统计时点，以免页面上各项数字跨秒出现不一致。

## 4. 数据结构与写入规则

增加版本化迁移 `backend/migrations/007_customer_acquisition_analytics.sql`。不要把结构回填写进启动时反复运行的 `backend/schema.sql`；现有 `DatabaseService` 会按版本在事务内执行迁移。

| 表 / 字段 | 用途 |
| --- | --- |
| `customer_acquisition.customer_id BIGINT PRIMARY KEY` | 外键指向 `customers(id) ON DELETE CASCADE`；一位客户只有一条获客归因。 |
| `initial_kind TEXT NOT NULL` | 创建时为“新线索”或“已有客户”，后续编辑 `customers.kind` 不改变它。 |
| `source_code TEXT NOT NULL` | 指向 `source_dictionary(code)`，保存获客来源；来源停用后历史归因仍可读取。 |
| `basis TEXT NOT NULL` | `captured`（创建时记录）、`legacy_snapshot`（迁移时按当前档案建立）、`manually_confirmed`（顾问明确更正并确认）。 |
| `recorded_at TIMESTAMPTZ NOT NULL` | 记录获客快照或人工确认的时间；获客群仍以 `customers.created_at` 分组。 |
| `customer_acquisition_corrections` | 保存 `customer_id`、改前/改后的初始身份与来源代码、原因、操作时间；随客户级联删除。 |

迁移给所有尚无获客记录的既有客户写入 `legacy_snapshot`，使用 `INSERT ... SELECT ... ON CONFLICT(customer_id) DO NOTHING`。由于现有 `schema.sql` 会在每次 API 启动、执行版本迁移**之前**重复初始化示例客户，迁移还需建立 `customers` 的 `AFTER INSERT` 触发器：以后任何路径新增客户时，立即用新行的 `kind`、`source_code` 写入 `customer_acquisition(basis='captured')`。这样首次迁移前的客户得到旧档案快照，后续启动时新插入的示例客户也不会漏记。触发器在客户插入的同一事务中执行；不在启动 SQL 中追加反复回填。建立获客来源与身份索引、`customers(created_at)` 索引、`customer_stage_history(customer_id,changed_at,to_stage)` 索引。迁移前后核对客户数与获客记录数；不得覆盖已有客户资料或修改历史阶段时间。

新增客户时，现有服务事务负责写 `customers`、初始 `customer_stage_history` 以及已有的可选待办；触发器在客户插入时同步写获客快照。任何一步失败全部回滚。普通 `PATCH /api/customers/:id` 继续更新当前档案的来源、身份或阶段；阶段变化仍写历史，但不得悄悄改写获客快照。

提供单独的“更正/确认获客信息”操作，允许修改有误的初始身份、获客来源，或对旧档案快照的现有值作人工确认；必须填写简短原因。服务端在事务中锁定获客行、校验来源代码并写更正记录，成功后更新 `basis='manually_confirmed'`。已确认的相同值再次提交属于无变化请求，不新增更正记录。客户详情应同时展示“当前来源”和“获客来源”，值不同的情况加简短说明。由于更正会改变历史统计结果，分析页重新请求聚合数据；不在前端自行改算。

## 5. 聚合规则与接口

新增只返回汇总数字的接口：

```http
GET /api/customers/analytics?from=2025-11-01&to=2026-10-18&sourceCode=referral
```

`sourceCode` 可省略；对日期格式、首尾顺序、24 个月上限和来源代码进行服务端校验，错误返回可读的 400。来源代码从字典查，包括已停用但有历史客户的代码；SQL 使用参数化查询。把路由注册在 `customers/:id` 之前，并在 `src/api.js` 增加对应方法。

响应结构以此为准，数字为整数、比率为 0–100 的一位小数或 `null`：

```json
{
  "asOf": "2026-10-18T10:00:00+08:00",
  "filters": { "from": "2025-11-01", "to": "2026-10-18", "sourceCode": "referral", "windowDays": 90 },
  "sourceOptions": [{ "code": "referral", "label": "朋友转介绍" }],
  "stageDistribution": {
    "total": 12,
    "items": [{ "stage": "新线索", "count": 3, "percent": 25.0 }]
  },
  "conversion": {
    "totalLeads": 7,
    "eligibleLeads": 4,
    "observingLeads": 2,
    "historyToReview": 1,
    "totals": { "contacted": 3, "needs": 2, "converted": 2, "deals": 1, "convertedRate": 50.0, "dealRate": 25.0 },
    "bySource": [{
      "code": "referral", "label": "朋友转介绍", "totalLeads": 7,
      "eligibleLeads": 4, "observingLeads": 2, "historyToReview": 1,
      "contacted": 3, "needs": 2, "converted": 2, "deals": 1,
      "convertedRate": 50.0, "dealRate": 25.0
    }]
  }
}
```

`stageDistribution.items` 始终按 `STAGES` 的六个值返回，零人数也保留；上例仅展示一项以说明字段。未选来源时 `bySource` 包含所选范围内有新增线索的来源，即使全部仍在观察中也保留该行；按 `totalLeads` 降序、来源代码稳定排序。`sourceOptions` 返回当前可选和历史上仍被引用的来源，保证停用来源也可筛选。`eligibleLeads` 与 `bySource` 各行分母均排除“观察中”和“历史资料待核对”。全局 `totalLeads = eligibleLeads + observingLeads + historyToReview`，来源行也满足同一等式。

聚合在后端数据库执行，按 `customer_id` 去重；里程碑人数只在“可完整观察”样本中统计，取每个里程碑第一次符合观察窗口的历史事件。计算转客户时对“已成交”和“已有客户”取最早一条，再按人去重。阶段跳级不补算“已联系”或“需求了解中”。查询使用固定 `asOf` 和一个一致的数据库快照；不要通过前端已加载的客户列表逐条扫描或对每位客户发详情请求。

另增加：

```http
PATCH /api/customers/:id/acquisition
Content-Type: application/json

{ "initialKind": "新线索", "sourceCode": "referral", "reason": "核对原始登记后确认" }
```

该接口返回更新后的获客记录。旧档案即使提交与快照相同的值，只要此前尚未人工确认，就完成一次确认并写审计记录；已确认后同值重试不重复写。客户端提交时显示加载状态并防重复；失败时保留表单输入和旧统计，提示可读错误。更新成功后刷新客户详情与分析接口。分析响应不包含姓名、电话或自由文本备注。

另提供 `GET /api/customers/acquisition-sources`，返回当前可用及仍被历史档案引用的来源代码与中文名称，供获客资料确认表单使用。

| 3. HTTP | `backend/api.controller.js`、`src/api.js` | 分析、来源选项和归因更正接口与服务门面同步；列表、详情和现有看板接口继续可用。 |

验收用例至少包括：

1. 当前阶段六类人数合计正确；同一客户在多个家庭仍只计一人；简要家庭成员不计入。
2. 同一线索先“已成交”后“已有客户”只算一次转客户，成交另算一次；直接建档的已有客户不进入转化分母。
3. 一条线索跳过“已联系”直接进入“需求了解中”或“已成交”时，只记录实际到达的阶段；重复变更或回退不重复累计。
4. 创建后第 89 天的线索属于“观察中”，满 90 天后才进入分母；第 90 天窗口边界前后的阶段事件按约定处理；跨上海日期边界筛选正确。
5. 修改当前来源不改变获客来源；显式更正会改归因、记录原因并使报表刷新。停用来源仍能展示其历史中文名称。
6. 缺少初始阶段记录的旧档案不会产生虚构转化；没有合格样本时显示“—”及排除原因。
7. API 错误、快速切换筛选、重复提交更正、删除客户级联、重复执行迁移、直达 `/clients?view=analysis`、窄屏和两种主题均按预期工作。

`npm run test:api` 必须显式连接**一次性可丢弃的测试 PostgreSQL 数据库**；不得指向实际客户数据库。再运行 `npm run test:ui-logic` 与 `npm run build`。浏览器核对分析标签、筛选、阶段修改后刷新、空样本提示和路由刷新；本期无需调用付费模型。

## 8. 下一阶段接口边界
